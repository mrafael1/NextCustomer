## 1. Pillars

Every feature must support at least one of these. If it doesn't, it waits.

1. **Coupons are the fun multiplier.** They create combinations that are impossible without them, and they bend the rules, not only the numbers.
2. **Scoring is readable.** It is deterministic and every payout is explained. The result can be ridiculous, but the logic is always clear. Every item wears a price sticker with its base value and a short effect, and scanning it (hovering it) shows its full rule and, on the belt, every line it adds to the receipt.
3. **Counting points feels great.** The receipt, the printer and the climbing total are the main reward.
4. **The art has a strong identity.** A warm boutique grocery for rich shoppers, with arcade warmth, in pixel art: chunky shapes, bold outlines, cream marble, brass and gold trim, velvet tomato-red accents and warm spotlights (style frame v2, section 6.1; the 1990s discount supermarket of v0.17 gave way to it on 2026-10-14).

Pillar 2 also covers choosing: every item the player can pick or score shows its sticker, and its rule one scan away. A view without rules (item sprites only, as on the figurine shelf) is a catalogue, never an item in the row.

Rules:
- Products, coupons, upgrades and inspections are **all made of the same rule hooks** (upgrades through `UpgradeRule`, which has the same hook names as `Rule` and is asked about every slot by the scoring loop; `docs/PROTOTYPE_PLAN.md` section 3.8). A new idea is a new rule script plus a data file, never a change to the scoring code.
- `score()` stays a pure function. All presentation plays back `ScoreResult.steps`.
- Save files include a format version from the first save. The profile save (decided with the user, phase 1) is `profile.json` in `user://`: JSON (it never runs code, unlike a resource file loaded from `user://`), written to a temporary file and then moved over the save. A profile that can't be read (bad JSON, a missing or newer format version, a field of the wrong type) is reported, kept as `profile.json.bad` (then `.bad.2`, …: a backup is never overwritten), and replaced by a fresh profile. A save that can't be opened or backed up is kept as it is and never saved over in that session; a failed write leaves the save unchanged. The run save (decided with the user, phase 1; `RunSave` in `core/`) is `run.json` next to the profile, a snapshot rather than a replay, with `format_version` 1. It holds what rebuilds the run (the seed, the impulse rack's offer, pick and replaced card, the listed aisle ids, the stock's card ids, `list_skipped` and the new arrivals; `run_start` logs the same) and the whole state: the starting deck, the deck's cards with their instance ids, the next instance id, the hand (with any debug-added card), the draw pile, the row in order, the redraws used and allowed, the shift, the phase, the reward, upgrade and next-inspection offers, the upgrades in pick order, the inspections, the history and the run RNG's state, plus the telemetry's `run_id` and the played time (`run_ms`). The seed and the RNG state are decimal strings, because JSON numbers lose precision above 2^53. Ids resolve through a `ContentLookup` (`data/<kind>/<id>.tres`, whose id must match the file name), and the stock comes from its saved ids, so a resume never depends on a profile that changed after the run started. A resumed run continues exactly as if it had never stopped: the same draws, redraws, offers and inspections. It is written at every stable point: the impulse rack shown, every shift's start, every place, remove and redraw, the checkout click (so closing the game during the count-up resumes on the reward screen; the profile of a run that ends is saved at the same click) and the upgrade tickets shown. Never mid-animation, and never a picked-up card, a redraw selection or the deck-full chooser (the reward panel shows again). A checkout that ends the run deletes it. A run save that can't be read gets the profile's treatment, with its own numbering (`run.json.bad`, `.bad.2`, …): bad JSON, a missing or newer format version, a field of the wrong type, an id that no longer resolves, or a state the game can't reach (a shift outside the run, another phase, a history that doesn't fit the shift, a row card not in the hand, a draw-pile card not in the deck, a repeated instance id, …); a new run then starts and overwrites it at its first save point. Deleting it also removes a leftover temporary file. The title screen reads it without reporting or backing anything up: with a readable save it shows Continue (shift N / M) and New run, and a background click starts nothing (Enter or Space continues); New run asks first ("Abandon the run in progress? It won't count."), then deletes the save and starts a new run. An abandoned run records nothing in the profile, like a restart before the end. The shift screen resumes the save when it holds a readable run and starts a new run otherwise. Telemetry: `run_resume` and `run_abandon` (`docs/PROTOTYPE_PLAN.md` section 8), and `run_end`'s `run_ms` counts played time only.
- The stock is built before `RunState` and passed in. It is ordered staples → listed aisles (aisle data order) → new arrivals → `coupon_pool`, each in data order, never by unlock order. Unlock recency ("newest first", section 7.2) only decides which new arrivals get in, not where they sit. The stored stock ids make replay independent of the profile.
- Derived streams (impulse rack, "Surprise me") are separate `RandomNumberGenerator` instances seeded from `hash([run_seed, "<stream name>"])`, created by the caller outside `core/` (`EventLogService.derived_stream`, next to the run seeds; the rack's stream is `impulse_rack`) and passed in, so `core/` still never makes a seed.
- `CardDefinition.art_ref` stays a path; presentation loads the sprite, so `core/` stays free of art. Since #75 every item is 48x48 art at 2x: a product's `art_ref` names its sprite (`art/items_v2/`), a coupon's names the icon drawn on the shared slip, and an empty `art_ref` shows the art-pending box (section 10).
- `CardDefinition.sticker_text` (#75) is the price sticker's short effect, a template with no digits ("+{bonus_each} per earlier {tag}"). `core/card_text.gd` (`CardText`) fills in its numbers, tags and names from the card's own rule (`sticker_summary()`), so the sticker never drifts from the rule; a variant with no template of its own uses its base card's. Bread and Potatoes have none: their sticker shows only the price.
- Aisles reference cards; cards stay flat in `data/cards/`.
- Any summary of a result (for example coupon credit) is computed and tested in `core/`, and only after its attribution rule is agreed.
- Tests run headless in CI (GdUnit4 GitHub Action) on every push.

## 5. Design frameworks

### 5.1 Coupons (the core)

Coupons fall into four types. 1.0 has at least 2 of each type, except Connector (at least 1, a second only if adjacency payoffs justify it).

| Type | What it does | Examples |
|---|---|---|
| **Connector** | Creates adjacency between products that are not neighbours | Shelf swap (the next product also counts as just after the row's first product; built in phase 2, v0.20) |
| **Relabeller** | Changes tags | Breakfast sticker, Clearance tag (the next product gains Clearance; built in phase 2, v0.23), Organic label (the next product gains Produce; held: every Produce reader is in Fruit & veg, so it would do nothing in a fresh profile or in lists without that aisle, v0.25) |
| **Amplifier** | Multiplies or copies | Repeat, Multipack, 2 for 1 (same product on both sides: the second one pays ×2; it fizzles otherwise, and two in a row both fizzle) |
| **Position** | Rewards placement | Final markdown, Opening deal (if in the first slot, the next product pays ×5, ×3 until v0.27; built in phase 2, v0.23) |

**Coupon slots (decided):** 6 shared slots + 1 coupon-only slot. A row holds at most `slot_count` products (6) and at most `slot_count + coupon_slot_count` cards (7); upgrades and inspections that add or remove a slot change one of these two numbers for the run or the shift. One coupon can take the coupon slot; extra coupons can still take product slots. Coupons in the row still break adjacency, so every positional coupon keeps its meaning and `score()` doesn't change. Every row that was legal before stays legal.

Good coupon rules:
- It creates a combination that **did not exist** without it, or it changes the best order of the row.
- Its effect fits in one line of rule text and one icon, and its price sticker's summary in two short lines (`sticker_text`).
- It has a cost: it uses a slot (the coupon slot or a product slot), or it only works in a certain position.
- It is not dominated: the simulator finds hands where removing it lowers the best score. (The prototype Bundle failed this: it only repaired the gap its own slot made.)
- No loops: a copy never triggers effects again, and coupons cannot copy coupons.

### 5.2 Register upgrades (designed carefully)

Upgrades last for the whole run. They live on the **loyalty card**: it starts empty (a starting deck's upgrade comes pre-stamped in a box of its own before the upgrade-shift boxes, section 7.3), each upgrade stamps one box and shows its perk icon, and the upgrade's receipt lines and count-up fly-ins come from that box. They are offered after the shifts in `upgrade_shifts` (2, 4 and 6), after that shift's normal reward pick or skip: the receipt goes into the exit kiosk, which drops up to 3 prize tickets (see the offer rule below), fully revealed (a cosmetic "INSTANT WINNER!" gag at most, never a hidden face). The exit kiosk sells nothing and is a separate prop from the capsule machines (section 7.1).

Good upgrades:
1. **Change what you draft or how you order cards.** A flat "+N to everything" is not allowed.
2. **Push towards a build without making it mandatory.** Each upgrade states which build it supports.
3. **Have a tradeoff or a condition.** For example "the first coupon in the row pays ×2", but only the first one, and only if it pays something (`docs/PROTOTYPE_PLAN.md` section 3.8).
4. **Use the existing hooks.** If an upgrade needs a new hook, it is a design flag to discuss.
5. **Are visible:** stamped on the loyalty card and named in the receipt explanation.

| Type | Example |
|---|---|
| Rule bender | Coupons no longer break adjacency (out of the pool since v0.27: it never raised a best row) |
| Slot engine | The 6th product ×2 (coupons don't count; since v0.27 the last regular product slot: the 5th on a Short belt shift, the 7th with Big basket) |
| Category engine | +3 per category present when the last product is scanned |
| Coupon engine | The first coupon's payout ×2 |
| Economy | +1 redraw per shift · +1 coupon slot ("+1 card drawn" was cut in v0.21: it overlapped the redraw) |
| Risky | One extra product slot, but the quota +15% |

Upgrade offers: 3 options, from different types, at least one fitting the current deck (since v0.21: builds are data files measured from the deck, `docs/PROTOTYPE_PLAN.md` section 3.8). The player must pick one: there is no skip. Every ticket shows the same fields in the same order: name, type, effect, condition (its own line), supported builds.

### 5.3 Inspections
Visible restrictions that test a build. One is announced before the previous shift's reward choice, printed as a red notice on the receipt under the total (before the kiosk on upgrade shifts). Inspections never go on the loyalty card. Never disable several parts of a build at once. Start with 3 of: only 5 product slots · the 3rd product pays 0 · duplicate payouts capped at 4 · the coupon slot is closed.

Phase 1 (decided, `docs/PROTOTYPE_PLAN.md` section 3.9): shifts 3, 5 and 7 are inspected, each with an inspection drawn from the pool with the run's RNG at the previous passed checkout. The placeholder is "the 3rd product pays 0", which behaves like Soup beside Frozen. During the shift, a red tag in the top bar shows it.

Phase 2 (decided, v0.22): the 3 are Spot check ("the 3rd product pays 0"), Short belt (one product slot fewer than the run has, so Big basket keeps 6) and Coupon slot closed (one coupon slot fewer), never the same one twice in a row. ### 6.2 Counting presentation (driven by `ScoreResult.steps`)

For each slot:
1. The item's sprite lifts as it is scanned (4 px off its mat, the view's `scan_lift()`) → beep. The handheld (#75) poses over it in gold, brackets and beam, as the lift starts (`ScanOverlay.pose_scan`; it never pulses and nothing waits for it), moves on to the next item's lift and docks in its cradle as the last beat ends
2. The base value pops up on the item's plaque
3. Each bonus flies in from the item that causes it (that item is highlighted) → the receipt prints a line
4. Multipliers land like a **stamp** (heavier sound, a bigger line)
5. The payout drops onto the receipt, the subtotal ticks up

Beats (decided with the user in v0.29, issue #60): before the count starts, a pure beat plan (`CountUpPlan`) turns the steps into beats, so the timing depends only on the steps, the shift and the settings. Every step keeps its beat and its receipt line, and the receipt still ends exactly as the instant receipt (`show_result`) prints it. Costs at ×1, start to start with a 60 ms trailing gap, live in `data/balance/count_up.tres` (`CountUpTuning`): pre-roll 120 ms, a plain card 240, an armed effect 160, a base on a non-plain card 130, a bonus 220 (190 from the card's own rule), a card stamp 240, an upgrade stamp 300, a payout override 240, a payout its roll + 60 (120 when it is 0), a fizzle 340 (a reset 480), a tag 260, a link 340.

- **Plain cards:** a card whose own steps are only its base and payout is one 240 ms beat: the lift with the beep and one note, the base pop, the payout line, a roll with 3 ticks (no roll on a zero payout). One beat per card, never one per run of plain cards, so the scanner rhythm and one payout per subtotal jump stay. A trailing armed or fizzle step keeps its own beat.
- **Armed effects** (Eggs charges, Coffee, Multipack) show as they are armed and travel to their targets: the arming card glows and punches, keeps a corner pip (its icon and "×3"), and sends one token per target at once (250 ms, not waited for). The plan matches targets in step order by source slot and text, with no change to `core/`; a later arming of the same effect takes over the landings after it. Each token parks on its target as a **dimmed target marker** (50% alpha, at the top right of the item's sprite, "×3 · Multipack", so not colour alone; with reduced motion it fades in) until its landing brightens and absorbs it. Landings keep their motion: a bonus flies from the causing card, a stamp slams at the target while the causing card punches. The pip clears after the last landing and turns grey for good on the effect's fizzle; tokens that never land dissolve at the row's end. Planning shows the exact projected total, and each step on its item (section 12).

Chips and the stub (#75, decided with the user on 2026-10-15): the CHECKOUT click clears the planning stub but keeps its header, and the steps print under it. It also clears every belt item's chips, and the tray dims. Each chip pops in (scale 1.3 to 1 over 0.18 s; it just appears under reduced motion) when its step lands (`CountUp.step_landed`, an upward signal). For a landing with a marker, the chip appears once the marker's absorb has finished, so a chip and its marker never show together. Every line boosted by another item, an upgrade or an inspection prints with a faint gold combo band, a gold bar and the combo diamond. Nothing waits for a chip and no beat was added, so the timing is unchanged. Turning the chips into the markers is left to #71.

Escalation (the inputs are the shift, the row's steps and the run's best checkout before this shift, at least €45; the quota never feeds intensity, so another quota gives the same count-up):
- The pitch climbs a musical scale across the whole row, not per card: an 11-note C major pentatonic ladder, G4 to G6. Only gains step it (a plain card, a bonus, a copy, a multiplier, from a card or an upgrade). With more than 11 gains the climb is spread (note = ⌊i × 10 ÷ (N − 1)⌋), so it never wraps or drops and the last gain lands on G6. An armed beat replays the current note at −10 dB; a stamp plays over the new note at −6 dB. Notes play on one player, so the newest cuts the last and skips can't stack them. Ticks keep one pitch at −8 dB, 3 per roll
- Intensity (printer speed, paper pile, rattle) follows the run: shift number, steps in the row, the run's best checkout. Not total ÷ quota, which shrinks as quotas rise. Printer speed = min(1.4, 1 + 0.05 × (shift − 1) + 0.01 × max(0, steps − 14)); a payout's roll is (110 + 50 × min(1, payout ÷ (0.25 × best))) ms ÷ printer speed, and the print sound's pitch is the printer speed, at most 1.26. A payout of at least max(€10, 0.2 × best) rattles the register by min(12, 3 + 6 × payout ÷ best) px, 2 px more (and a stronger subtotal punch) once the subtotal has passed the best, with no label. A paper pile on the counter at the hanging receipt's foot (#55: receipt paper fed from the printer, drawn in the art palette) starts at 6 px per earlier shift (at most 42), grows 2 px per printed line, up to 120. The €45 floor and the €50 below are the v0.27 simulator's shift 1 median (`greedy@sensible`), copied by hand into the tuning
- The subtotal changes colour (mustard to green) with a short ding (a C6 bell) and a 100 ms hit-stop when it reaches the quota, unless that happens on the last payout; then the colour comes with the total line. Either way a lasting "✓ QUOTA" chip (icon and label) pops in on the register LED's quota line (over "QUOTA €N", #55) and stays there while the LED shows the SUBTOTAL or TOTAL; it hides when the LED switches to the next shift's PROJECTED total. Nothing is added to the receipt, and a fail never shows the chip
- Large totals (at least max(€50, 1.25 × best)) make the register rattle (8 px; huge totals, at least 2 × best: 12 px, and the paper curls and spills), with a short pause before the final total: 300 ms, 500 when large, 700 when huge. The printer goes silent and the last note rings out
- Total vs quota: a clear pass / fail moment. The count-up ends when the total line prints (with a 1.5 subtotal punch) and hands its intensity (rattle, large or huge, reduced motion) to the dessert, which owns the verdict's slam, the pass and fail sounds and the shake (issue #61). The count-up plays no pass or fail sound

The dessert (decided with the user in v0.31, issue #61): about 1 s from the verdict to a clickable reward. The verdict is the moment the TOTAL line prints (`total_shown_ms`). The dessert's times live in `data/balance/count_up.tres` (`CountUpTuning`, the Dessert group). They run at the speed setting (Fast ×1.5) but not at the automatic ×1.25. A pass with no taps at Normal speed, in ms from the verdict:
1. **Silence.** The music ducks as #60's pause before the total starts, not after the verdict, so the slam lands in near-silence without an extra hush (section 6.3)
2. **The slam (100–300).** "€total / €quota" slams once onto the receipt's TOTAL line (no re-count), green on a pass and red on a miss. It lands with `total` (or `miss`) and a shake: 10 px on a pass, 4 on a miss, a quarter more for a large total and half more for a huge one
3. **The margin (300–500).** A line under the total counts up "+€N OVER QUOTA", or "SHORT €N" in red, or "ON QUOTA" in green when the total is exactly on the quota (`ShiftMargin` in `core/`; `CoinPayout` is untouched). `pass` (or `fail`) plays at about 450. Section 12's overshoot tiers are not added
4. **PAID (520).** Every passed shift, shift 8 included, gets a tilted PAID stamp (`stamp_paid`) on the margin line once it has counted
5. **The tear (560).** The receipt tears (`rip`) under its lines on every shift. On a miss it tears after `fail` has rung out, with the music still ducked. When the next shift is inspected, its notice prints in red under the tear (with `print`, then `stamp_notice`), inside the same 1 s
6. **The print-out (700–850).** On a passed shift that isn't the last, the printer feeds the reward print-out, the music comes back over 600 ms and the offer's timeline starts. The print-out sits on the stage beside the receipt, and the shade stops at the register's column, so the register, the receipt and the paper pile stay unshaded (#55). It drops the repeated headline but keeps the red inspection warning, so the notice shows on both. Its offers lift out of the printer as tray items over 150 ms (#75), and products wear a cosmetic PROMO tag, tilted on their price sticker over the glyph corner (no data change). The impulse rack shows tray items too, and both can be scanned once the panel accepts clicks (section 6.1). The print-out arms as soon as the lift has ended and the mouse is up, with no fixed 350 ms wait. Skip, View deck, the deck count, the deck-full chooser and the warning keep working, and the deck view and the chooser show it again without replaying it. On upgrade shifts the exit kiosk follows the pick (#66)

The test budget is 1,000 ms from the verdict to the armed print-out, at Normal speed with no taps, plus 150 ms for frame boundaries; a run measured 876 ms. A miss reaches the results at about 2.2 s, with no budget. A lost shift and a won shift 8 have no print-out: their dessert leads to the final receipt. A longer first-time dessert was declined. Resume is unchanged and adds no save point: a resumed reward has no dessert, and its print-out is shown already lifted, on a new timeline.

The run's dessert is the final receipt on the results screen (`ui/final_receipt.gd`, shown by `ResultsPanel`). It replaces the old headline, run history and coin receipt and keeps their content. From the top:
- the headline, "RUN WON!" or "RUN OVER", in green or red
- one line per played shift: its number, €total / €quota, pass or fail, and the card picked (or "skipped"), with the upgrade taken and the inspection played under on a dim second line
- on a lost run, the shortfall ("Shift 3 / 8: short by €12")
- the coins at the bottom: shifts passed, overtime, then the run's coins and the profile's total ("you have ?" when the profile couldn't be saved)

It prints line by line, one every 80 ms (`final_line_ms`), and a tap prints the rest at once (its own press reader). The coin sounds and the music's 18 dB duck start when the coin lines print, a skipped print included. The loyalty card, with its starting-upgrade box, is stapled to the top-right corner beside the headline and covers no line. New run keeps its 350 ms / mouse-up arm, so it can be clicked mid-print; Export log stays.

Time budget: about 4–6 s for a full row, about 1 s from the verdict to a clickable reward, about 1.2 s to the kiosk choice (longer variants play once per profile). When the beat plan's `planned_ms` (click to total shown, at the current speed) is over 5,500 ms, these stages apply in order, each in full, until the row fits: trailing gaps 60 → 40 ms; the 2nd and later landings of one armed effect become 140 ms echoes with no hit-stop; payout rolls at most 100 ms; flights, tags and links ×0.75 (flights at least 150 ms); a uniform factor up to ×1.3. Never shortened: the ding and its hit-stop, the first stamp on each card, the pause before the total, a fizzle's grey hold (at least 300 ms) and plain beats. The fit never looks at the quota. Rows with no effects stay under 4 s by design (7 plain cards: about 2.1 s).

Respecting the player:
- A tap speeds the count to the verdict; a second tap (or a first one after the verdict) skips the dessert at ×30. A skipped dessert still plays every line and sound, only faster, and leaves the same receipt. A tap during the print-out's lift skips it too. Either skip sets `presentation_skipped` on the reward, so on passed shifts it mostly equals `dessert_skipped`. The print-out arms only once the mouse is up, so the skipping tap never picks an item. A hold fast-forwards (a press-time threshold separates the two; the checkout click's release is ignored). Skips speed tweens up, they never kill them. The tap and the hold are built in phase 1 (200 ms threshold; `docs/PROTOTYPE_PLAN.md` section 8). The count speeds up automatically from shift 3, by a flat ×1.25 (the printer speed carries the further rise), times the speed setting; the fastest of the tap, the hold and that speed wins. `count_up_ms` keeps its meaning (click to final total shown, the pause included); skips are logged separately, and since v0.29 so are the speed, the settings, the step count and `planned_ms` (`docs/PROTOTYPE_PLAN.md` section 8)
- Pauses (hit-stop) pause the count-up's own tweens, never the engine's time scale. They last real milliseconds: 50 on a card's first stamp, 70 on an upgrade stamp or a payout override, 100 at the quota ding. Hit-stops starting within 200 ms of each other merge, keeping the longest. Taps and holds shorten them and the pause before the total; the automatic speed-up and the speed setting don't
- Speed settings (Normal ×1, Fast ×1.5); reduced motion (no shaking, a calmer count): no rattle or shakes, markers fade in instead of flying, the pile grows without bouncing; hit-stops stay. In the dessert, the slam fades in at full size, nothing shakes and the print-out's items fade in in place; the small punches and the timing stay. Both are profile settings, on temporary debug toggles until phase 4's settings screen
- The receipt is always a straight, readable list, even when the paper curls (the pile is decoration; receipt lines are never rotated)
- The paper pile was hidden until #55's register drew it as receipt paper coming out of the printer (decided with the user in v0.29: on its own, a stack of strips beside the receipt read as noise). Since #55 (v0.32) it shows on the counter once the receipt reaches it, its top fold joined to the receipt's foot
- No information is shown only inside an animation (the pip, the "✓ QUOTA" chip and the green subtotal last)

### 6.3 Sound

Decided with the user in v0.30 (issue #62), after the `fb-p2` players disliked every synthesised placeholder: pleasant, soft-edged recordings that still make the count juicy.

- **Sources:** real recordings, all CC0 1.0 (no attribution; safe in the public repo, on Steam and in the web build), each licence checked on its page on 2026-10-12: Kenney's Interface, Impact and Casino packs, Freesound recordings and VCSL instrument samples (xylophone, glockenspiel, hand chimes, bell tree, marimba). Short, trimmed excerpts live in `audio/src/` (ignored by Godot), each pack's licence beside its files and the Freesound IDs in `audio/src/freesound/ledger.tsv`; `audio/src/README.md` says where each came from and how it was cut. Only the scan beep (a soft sine at C7, above the ladder) and the fizzle are synthesised. Nothing is commissioned for now
- **Build:** `tools/make_sfx.py` (Python standard library, deterministic) is the single step from `audio/src/` to `audio/sfx/`: it folds each excerpt to mono, cuts, resamples (a windowed sinc), filters, layers and fades it, and normalises each sound to its `GAINS` peak, writing mono 16-bit 44100 Hz WAVs (was 22050). Its test checks that two runs write the same bytes and that the committed files are up to date. Review time is logged per sound in `audio/src/production_log.tsv`, as for art (section 6.1)
- **The set:** 60 files with fixed names (`Sfx.SOUNDS`), the contract between the build and the game. The count-up: `scan`, `print`, `tick`, `stamp` (multipliers), `stamp_loyalty` (the upgrade ticket), `stamp_notice` (a light self-inking stamp for the inspection notice), `rattle_s` / `rattle_m` / `rattle_l` (by the rattle's size), `register_bell` (huge totals), `ding` (a glockenspiel with hand chimes), `tag`, `link`, `copy`, `fizzle`, `denied` and `armed` (a soft bell-tree shimmer under the replayed note; it goes if it feels busy). The dessert (#61): `total` and `miss` (the verdict's slam), `pass`, `fail` (a soft marimba descent), `stamp_paid` and `rip`. Cards and UI: `card_place` (real card-on-table takes), `card_pickup`, `card_return`, `slot_tick` (each new slot under a dragged card, at most one per 60 ms), `fan` and `shuffle` (the redraw and the deck view), `checkout` (a register key clack), `ui_click` (every `UiKit.button`), `ui_open`, `ui_close`, `ui_back`, `ui_confirm`, `ui_switch`, and `coin` per coin on the final receipt (at most 15). No hover sounds, with one exception (decided with the user for #75 on 2026-10-15): the hover scanner's beep, `scan_hover`, an alias of `scan` (`Sfx.ALIASES`, so no new file) played at −8 dB. It plays only when a new item is scanned, at most once every 120 ms, never while dragging or counting, and is counted apart from the count-up's `scan`. Items keep the card sounds (`card_pickup`, `card_place`, `card_return`, `fan`). The placeholder `bonus` and `click` are gone
- **The note ladder:** 11 files, `bonus_00` (G4) to `bonus_10` (G6), from the VCSL xylophone. G4, C5, G5, C6 and G6 are exact samples; the other notes are shifted at most 3 semitones, and each sample's measured tuning offset is removed, so every fundamental is within ±25 cents (tested). The timbre brightens up the ladder (soft mallets pp low, soft ff in the middle, medium ff at the top, the peak rising from 0.40 to 0.52), and each note lasts about 0.9 s, so the last one rings into the pause. `Sfx.play_note` plays the file for its index, clamped to 0–10; nothing is pitched at play time. Section 6.2's levels hold: the stamp keeps its own sample over the note at −6 dB, an armed beat replays the note at −10 dB
- **Round-robin takes:** `stamp` (3), `card_place` (4), `card_pickup` (3), `card_return` (2), `ui_click` (3) and `coin` (3) are numbered takes (`stamp_1` …). `Sfx.play("<base>")` cycles them in a fixed order, one counter per sound, so a run sounds the same every time
- **Buses and ducking:** `default_bus_layout.tres` has Master, Music and SFX (it is in the resource-loading test). SFX sits at −6 dB, so coinciding sounds don't clip, and Music at −15 dB, 9 dB under SFX. Levels are bus volumes because bus effects don't run on the web build. The dessert ducks the Music bus by 24 dB (to −39 dB) over 120 ms as #60's pause before the total starts (section 6.2), so the slam lands in near-silence at least 600 ms into the duck, and the music comes back over 600 ms at the printer feed, when the reward print-out appears; on a fail it stays ducked through the fail sound, then crossfades to the results loop; a second-tap skip brings it back over 150 ms. The final receipt ducks it by 18 dB (to −33 dB) while the coins print, until one coin gap after the last coin and at least 1 s
- **Music:** two CC0 loops from OpenGameArt, with their licences and credits in `audio/music/LICENSE.md`: "Buy Something!" by Cleyton Kauffman (the normal mix, credited as he asks) on the shift screen (`audio/music/shift.ogg`), and "Urban Shop" by MintoDog on the title and results screens (`front.ogg`). The user picked both by ear on 2026-10-12; they are re-encoded once (OGG Vorbis quality 5 with a gentle 1–3 kHz dip to clear the note ladder and the beep, about 3.4 MB for both, each step recorded in `LICENSE.md`); the fallback is "headscratcher" by congusbongus (OGA-BY 4.0, with attribution and a change notice). Both are imported with loop on and loop offset 0, so a track is swapped by replacing its file only
- **Players:** the `Music` autoload (`presentation/music.gd`) is a global service. It holds playback state only (the track, a 0.8 s equal-power crossfade and the duck), never run state, plays on the Music bus, takes an injectable error reporter and ducks through `duck()` / `unduck()` (the bus volume, or the players' `volume_db` without that bus). Browsers block autoplay, so the music starts on the title's first click (a click that starts the run leaves it to the shift screen's loop); headless runs (tests, tools) load no streams. Sound effects stay in their scenes: each scene has its own `Sfx`, which warms up every sound silently when the title or the shift screen opens, so the web build never hitches mid-count
- **Still open:** the feedback at the end of phase 3 (the release-candidate playtest, issue #69) can change small details of the sound and the music, their direction, and even swap assets. The fixed names and the file-only swaps above keep such changes cheap

## 7. Unlocks: capsule machines, aisles and decks

Design rules (from the original doc): **unlocked decks have comparable starting strength**. Unlocks add options, not raw power. No permanent payout increases.

### 7.1 Capsule machines
One capsule machine per aisle at the store exit, like the coin-op toy machines that sell little figurines. 1 coin = 1 capsule: a fixed price, no shop, no second currency, nothing for sale, no microtransactions.

- **Coins** print at the bottom of the final receipt, as part of the run's dessert: more the further the run got, a little for overtime, something even for a lost run. The amounts live in balance data. Decided with the user (phase 1, `CoinPayout` in `core/`): `coins_by_shifts_passed[shifts passed]` (index 8 is a won run), plus one overtime coin per `overtime_coin_euros` of margin over quota summed over the passed shifts, at most `overtime_coin_max` (1). A run lost early pays no table coins, so losing fast doesn't farm capsules (it can still earn the overtime coin, which is very unlikely that early); a typical run pays 1, a won run 2, a great win 3. **Amounts fitted with the simulator (v0.26, issue #41, decided with the user):** the table 0, 0, 0, 0, 1, 1, 1, 1, 2 (no table coins for a run lost on shifts 1 to 4; phase 1 had shifts 1 and 2) and one overtime coin per €700 (fitted at €723 so that just over 1 run in 10 earns it, rounded down: 11% of runs; a shift-1 margin alone never reached it). On the fresh profile the sensible player's runs pay a mean of 1.18 coins, the median run 1 and a great run (p90) 3. Played as chained profiles (section 8), whose stock grows with each capsule, they unlock all 30 items in 27 runs at the median (23 at p10, 37 at p90), paying 1.05 coins a run. Keeping the phase-1 table (a run lost on shift 3 or 4 paying 1) would have paid 1.40 a run, about 21 runs, under the target. **Refitted in the balance passes (v0.27, issue #42):** the same table, and one overtime coin per €923 (fitted on 1,440 runs of the sensible player on the v0.27 data: 10% of runs earn it); a mean of 1.17 coins a run, the median run 1, a great run (p90) 2, 30 unlocks in about 26 runs. When the profile can't be saved, the results print the run's coins but no total ("you have ?"). The final receipt (section 6.2, v0.31) prints the breakdown at its bottom (shifts passed, overtime, then the coins and the profile's total), each coin clinking as the coin lines print, and the title screen shows the total.
- **The draw:** the player picks the machine; the draw inside it is random, without duplicates, until the machine is empty (that aisle's collection is complete). The first capsule from each machine is always the aisle's key item, so later items have something to combine with.
- **The figurine:** the capsule holds the item's figurine, its plain card sprite. Unlocked figurines go on the shelf, which doubles as the catalogue (items without their cards).
- **Unlock unit:** an aisle's items through its machine, never orphan random cards from the whole catalogue. Unlocked items join the run's stock (section 7.2), which feeds the impulse rack and reward offers.
- **Pacing target:** about 1 capsule per average run, 2–3 for a great run. About 30 unlocks, finished in about 25–40 runs.
- **Wording:** "capsule machine" in this plan; in-game copy may also say "toy machine". Never "gacha", in the game or on the store page.
- **Separate from the exit kiosk:** both are props at the store exit, but the kiosk offers the mid-run upgrades and stamps the loyalty card (section 5.2). They look different and do different things.
- **Phasing:** coins on the receipt and the saved unlock state in phase 1; the machine, its animation and the figurine shelf in phase 3.

### 7.2 Run stock: the shopping list
**Unlocks widen the choice between runs, never the pool inside a run.** Offers are uniform draws, so offer quality depends only on how many products are stocked. The target is about 20 products, whatever the collection size.

Each run stocks, in data order:
1. **Staples:** the starting deck's own products (starter: Banana, Bread, Milk, Eggs, Coffee, Soup), derived from the `DeckDefinition`. Always stocked, no machine. In the starter they hold all 4 `generally_useful` cards (Banana, Bread, Eggs, Milk), and every deck's staples hold at least 2 (a data test), so the reward guarantee always has a candidate. Aisles may add up to 2 more each. A later deck brings its own staples.
2. **Listed aisles**, whole aisles only. If every listable aisle together holds at most `aisle_stock_budget` (16) products, all are stocked and the list is skipped (new profiles, the tutorial, the web demo, or a cut machine). Otherwise the player lists `run_aisle_picks` (2). An aisle is listable once it holds `aisle_listable_min` (4) items; the minimum applies to machine-opened aisles only, so an aisle with `base_cards` is always listable.
3. **New arrivals (the end-cap):** up to `end_cap_max` (3) items from unlisted aisles that came out of a capsule in the last `end_cap_window_runs` (3) runs, newest first. Decided with the user (phase 1): the profile keeps, in draw order, each unlocked item's run index: the 0-based index of the run at whose exit it came out (that run's count of earlier runs, not the count after it ended); a run with index N (N earlier runs) takes items with index N − 3 to N − 1, so a capsule from run K rides runs K + 1 to K + 3, newest first by run index, and within one run the later draw first. The newest takes one impulse-rack slot. A machine-opened aisle that is not yet listable reaches the run only this way: each of its items rides the end-cap for the 3 runs after it came out (decided with the user, phase 1: the window applies to every capsule item), so its early items can leave the stock before the aisle holds 4 and becomes listable. A capsule is always playable in the next run.
4. **Coupons:** all of `coupon_pool`. Coupons are never in aisles or capsules.

Reward offers keep the prototype's rules (`docs/PROTOTYPE_PLAN.md`, section 5) and draw from the stock: the first offer includes a combination coupon, every later offer has at least 1 coupon and at least 1 `generally_useful` card, and an offer never shows a card twice. The impulse rack shows `impulse_rack_size` (3, balance data) stocked products in random order, the newest new arrival in one of its slots; the player picks one for the deck or skips. Decided with the user (phase 1): at the deck limit a rack pick removes a deck card, as a reward pick does. The rack comes before shift 1's draw, so the pick can be drawn in shift 1.

The reward prints from the receipt as the reward print-out: coupons plus promo products (stocked products on special offer, shown as full cards).

**The shopping list:** a note at the register before the impulse rack. It is pre-filled with the last list (the first time, with the newly listable aisle if there is one, otherwise the two base aisles with the most unlocked items, ties by data order), and one click clocks in. "Surprise me" picks a pair from a derived stream (section 4). The list stores a preference, never power. No per-item toggles, ban lists or figurines turned to the wall: players would prune to the strongest cards. Also rejected: ticketed offers (a rule change with a new hook on every rule), a seeded-only flyer as the default (kept only as the fallback if the note is cut), and a stock-size valve (the 9-item aisle cap replaces it).

**Content shape (1.0, decided; built in phase 2, v0.25, issue #35: Cold cases, Pantry and Household grow to 7 items each, and Fruit & veg, Bakery and Snacks open through their machines; `docs/PROTOTYPE_PLAN.md` section 5 lists every item; easy to change later, because the stock rule works with any number of aisles):** 6 staples · 3 base aisles open from the start (5/5/4), whose machines add 2–3 each, to about 7 · 3 aisles opened by their machines (8/8/7) · 30 capsules, about 50 products · at full collection, 15 possible lists of 20–22 products (plus up to 3 new arrivals).

**Aisle rules (data tests):** every product is a staple or in exactly one aisle · 6–9 items per complete aisle · at most 2 `generally_useful` per aisle · the capsule list starts with the key item · every deck's staples hold at least 2 `generally_useful` products. Simulator rule: every key item and capsule item reaches the best row with a staple or its own aisle, so nothing is an orphan while it rides the end-cap.

**Saves and replay:** building the stock uses no RNG except "Surprise me". The stored stock (section 4) means a resume never depends on a profile that changed after the run started.

### 7.3 Decks and card variants (architecture now, content after launch)

The prototype already has `DeckDefinition` (id, name, cards) and data-driven cards. Phase 1 adds the remaining fields below, so adding decks and variants after that is a content task:

- `DeckDefinition`: id, name, description, card list, starting upgrade (optional), unlock condition. Its distinct products are its staples (section 7.2)
- `CardDefinition.variant_of`: card variants (e.g. "Organic Banana" as a variant of Banana), with their own optional unlock condition. A variant is a variant of a card that is not itself a variant, of the same kind (a data test)
- `ProfileState` (fields in section 4) holds the deck and variant unlocks. Saved separately from the run.
- Unlock conditions are data (`UnlockCondition`: kind, card, amount) and are checked when a run ends. No condition means available from the start. Decided with the user (phase 1):
  - **Win a run with X:** X is a card in the run's final deck, and the run must be won.
  - **Score Y in one checkout:** any checkout of the run that just ended totals at least Y.
  - **Use coupon Z N times:** across runs, every copy of Z in a checked-out row counts once. The run history records each shift's checked-out cards; earlier runs' counts come from `ProfileState`.
  - The check is pure (`UnlockCheck`, tested in phase 1). At the end of a run (won or lost), `ProfileState.record_run` checks every locked deck and variant in `data/catalogue/catalogue.tres` with the coupon counts from before the run, then adds the run's coupon uses and counts the run; the profile is saved at the checkout click. Decided with the user (phase 1): a run restarted before its end records nothing.
- **Starting upgrade (decided with the user):** a run started with a deck that has one owns it from the first shift. Upgrade offers skip it like any owned upgrade, it counts for redraws and scoring, and the loyalty card gives it a pre-stamped box of its own before the upgrade-shift boxes. The starter deck has none.

Possible ideas: Breakfast deck (start with Coffee and Milk), Coupon deck (fewer products, 2 starting coupons), Frozen deck (Frozen peas, Soup risk).
Card changes: unlock variants that replace a starting card (e.g. swap 1 Banana for an Organic Banana in the run start screen).

**Basket Rush (after launch):** a shopping screen that builds the starting deck. One limit: item prices in data plus a fixed basket size (a size limit alone allows 6 Eggs + 6 Milk). Dexterity never changes what ends up in the deck. It remembers the last basket, is skipped on the first run and in the web demo, and has a static mode for reduced motion. Its strength spread is checked with the simulator's run win rates.

## 8. Balance simulator

A command-line tool, run headless, that uses `core/` directly:
- For a given hand, it tries every selection and order of up to 7 cards with at most 6 products (section 5.1), including shorter rows, because a shorter row can score higher, and finds the best possible score. That is up to about 69,000 rows for a hand of 8 (40,320 seven-card rows plus the shorter ones), and about 1.6× more when an upgrade adds a slot (Extra coupon slot or Big basket; with both, the hand of 8 still caps a row at 8 cards). "+1 card drawn", which would have made it about 4×, was cut in v0.21
- It simulates thousands of seeded runs with simple drafting strategies (greedy, build-focused)
- Outputs: the distribution of best scores per shift (to set quotas), win rate per build, how often each card is in the best row (finds dominant or useless cards)
- Models the redraw, the coupon slot, the impulse rack (picked with the strategy's reward rule, decided with the user, phase 1) and a starting-deck parameter
- Reports per-shift score percentiles (used for count-up intensity) and flags dominated cards (removing them never lowers a best score)
- Values coupons against other coupons per coupon slot, not against skipping
- Takes a stock parameter. List gate: every legal list at full collection, plus the minimum states (a new aisle at 4 items, the first list after the budget is passed), has a run win rate within ±5 percentage points of the fresh-profile stock's, and no list pushes a build over the 40% bar. Reports the per-offer chance of seeing a build's key cards; at full collection it stays at least 85% of the fresh profile's
- Reports coins per run from the balance-data coin amounts; they are tuned so the median run pays about 1 coin, a great run 2–3, and the 30 unlocks take about 25–40 runs (section 7.1)
- **Built in phase 2 (v0.24, issue #40), decided with the user:**
  - **Collection states.** `--profile=<save>` stocks the runs as the game would for that profile's next run (its unlocked items, run count and last list). `--collection=full` unlocks every capsule item, with no new arrivals. `--list=a+b` gives the list.
  - **List gate.** `--list-gate` plays the fresh profile and every gate state, then reports a pass or fail line for each state:
    - every legal list at full collection;
    - every list of the first state that needs one (base-aisle capsules unlocked in turn until the budget is passed);
    - each machine-opened aisle just listable at `aisle_listable_min` items, with every list that holds it.

    The gate states have no new arrivals. A state passes when, for each strategy played, its win rate is within ±5 points of the fresh profile's (inclusive, counted exactly). At full collection each build's key-card chance must also be at least 85% of the fresh profile's. A main build over the 40% bar was a failure until v0.27 and is now a warning printed beside the verdict (issue #42). A strategy with no runs on either side (the time limit) fails the state: there is nothing to compare. The gate shares `--max-minutes` between every state, so give it more time.
  - **Builds.** A build is a `data/builds/` file (section 5.2). Each run gets one **main build**: the build its final deck fits most strongly (measure ÷ `min_count`), or "no build". The **40% bar** is a main build's share of the greedy strategy's won runs; runs that fit no build count among the won runs but are never held to the bar, and the gate needs the greedy strategy. A `build:<id>` strategy drafts towards one build, to show which builds are viable (revised in v0.27, below). A build's **key cards** are the cards that count towards its measure on their own.
  - **Coins.** "A great run" is the 90th percentile of coins per run. Runs to 30 unlocks is 30 ÷ mean coins at the given stock. Chained runs, whose stock grows with each capsule, are left for the reward-economy pass once the capsule aisles exist (built in v0.26, below).
  - **Orphan check.** It samples hands of each capsule item with the staples and its own aisle, and flags an item that is never in a best row.
  - **Run modifiers.** Already handled before this issue: every shift's row limits and redraws come from `ShiftLimits`, and the search cache keys each hand by those limits.
- **Built in phase 2 (v0.26, issue #41), decided with the user:**
  - **Sensible rows.** "A sensible but not optimal order" is a row player, not a share of the best: a strategy ending in `@sensible` (e.g. `greedy@sensible`) places the hand in draw order, then makes up to 3 changes, each the single move, swap, addition or removal that raises the preview most (`SimHillClimb`). Its redraws replace the cards its row leaves out, and after each redraw it makes up to 3 more changes from the row it kept, as a player rearranges once new cards arrive (decided with the user). The greedy valuation plays its sample hands the same way, and each shift still records the exact best row beside it: in the runs, the sensible rows reach 96% of it on average. `tools/row_calibration.sh` replays logged checkouts through both: on the 101 logged hands, an uncapped climb reached the exact best in 78% of them (98% of it on average, practically optimal), 3 changes in 45% (94% on average, 82% at p10). The logged players scored 44% of the best at the median, but against quotas of about 10, so they show no effort and can't calibrate it; the next playtest on the new curve can. A climb that starts from an empty row was rejected: it stops at two cards when every single addition lowers the total (Category engine), which no player does.
  - **Curve fitting.** No simulator choice reads the quota, so a run played with `--quotas=0` is, shift for shift, the run of any curve until its first failed shift. `--records` writes every run, and `tools/quota_fit.py` replays them under a candidate curve and coin amounts (Big basket's raise from the shift after its pick, the coins as `CoinPayout` pays them) and fits both to the targets below. It also reports, per inspection, its share of the failed inspected shifts; per upgrade, the win rate and the pass rate of the last two shifts; and per card, the pass rate of shifts whose hand held it against those whose hand didn't (each shift records its hand).
  - **The quota curve** (in `data/balance/balance.tres`): 41, 42, 65, 77, 87, 123, 124, 149, fitted on 480 `--quotas=0` runs per strategy on the fresh profile. Targets: the sensible player with greedy drafting (`greedy@sensible`) passes shift 1 in at least 97% of runs and shift 2 in at least 95% of the runs that reach it; from shift 3 every shift fails the same share of the runs reaching it, set so it wins 35–40% of runs; each quota is the highest whole number the required share still meets, but the curve rises by at least 1 a shift. Result: shift 1 passes 97.1%, shifts 3 to 6 and 8 fail about 13% each, and the run is won 37.5% of the time. Two shifts are held at that floor and miss their share: shift 2 (42, one over shift 1, because its hands are no stronger than shift 1's) passes 94.2%, just under 95%, and shift 7 (124, inspected) fails about 18%; the fitter warns about both. A smoothed curve (40, 45, 58, 72, 88, 108, 125, 150) was rejected: it drops shift 2 to 91%. Skip (the starting deck, upgrades still picked) wins 22.9% and random drafting 4.6%, so drafting adds only about 15 points over skipping every reward: upgrades carry the run (the shift-8 median is 245 skipping, 257 drafting). Quotas can't widen that, so "skip at least 25 points below greedy" moves to the balance passes (#42) as a gate item, with these findings: Short belt causes 56% of the failed inspected shifts while it is a third of them, runs with Rule bender win 25% and with Category engine 61%, and Big basket is almost never picked. The card checks on the new curve (480 runs per strategy, played with the live data, which reproduce the fit exactly; pass rates are the sensible player's on shifts 2 to 8 with the card in hand against without it): Eggs is still a single point of failure (90% against 66%), and so is Milk (90% against 64%); Multipack still dominates (99.5% of the coupon-slot duel; 94% against 85%); Breakfast sticker is still near blank (6.7 under the average coupon, never the best); and a hand holding 2 for 1 passes only 68% (89% without). All of it goes to #42.
  - **Chained profiles.** `--chains=N` plays N profiles per strategy from a fresh one, run after run (at most `--chain-runs`), each run's coins buying capsules (a random machine with items left, its key item first, then at random), the list kept and joined by an aisle once it becomes listable, and new arrivals riding the end-cap as in the game. It reports the runs to unlock all 30 items (p10, median, p90). On the new curve and coins, 24 profiles of the sensible player took 27 runs at the median (23 at p10, 37 at p90), inside the 25–40 target, at 1.05 coins a run; their win rate falls from 37.5% on the fresh profile to 33% over the chain as the stock widens, for the list gate in #42 to watch.

- **Changed in phase 2 (v0.27, issue #42), decided with the user:**
  - **The build player.** The #40 `build:<id>` strategy took a card that raised its build's measure at every offer, with no end, swapped one key card for another at the deck limit, and always took the first offered upgrade listing its build. That measured the player's mistakes: Coupon specialist won 7% with it, against 41% in the greedy runs that ended as a coupon deck, and no build was viable. Now it drafts towards the build only while the deck's measure is under `min_count` + 2 (`BUILD_MARGIN`), then drafts as greedy; at the deck limit it never lets go of a card whose loss lowers the measure while the measure is at most `min_count` + 2; and it takes the offered upgrade listing its build only when greedy values it at least 95% as much as the best offered upgrade (`LISTED_UPGRADE_SHARE`). On the v0.26 data that alone made 3 of the 5 builds viable (Breakfast special, Coupon specialist, Mixed basket).
  - **The 40% bar** is a warning in the report and the list gate, not a failure.
  - **Viability's formation check** (section 4, phase 2) counts the runs whose final deck fits the target build, no longer the runs whose main build it is: the main build divides each measure by its `min_count`, so 2 Clearance cards lost to 7 tags of Mixed basket even in decks drafted for Clearance. Each run record lists every build its final deck fits (`fitted_builds`), and the report prints "Target build <id> fits the final deck: N of M runs" for each `build:<id>` strategy.
  - **The card package and the refit.** The content changes are in `docs/PROTOTYPE_PLAN.md` v0.29: Final markdown replaces Repeat in the starting deck; Multipack ignores Food and Breakfast and pays ×3; Slot engine doubles the last regular product slot; Rule bender leaves the pool and Big basket also lists Bulk buyer; Eggs has 1 charge, Bread 5, Milk 4 +1, Tea bags ×4, Carrier bag +5, Opening deal ×5, Final markdown +4; Reduced yogurt and Flickering bulb are generally useful and Clearance tag counts toward Clearance collector. The quotas were refitted with the #41 targets: 34, 35, 53, 61, 73, 98, 111, 120, fitted by `tools/quota_fit.py` on 1,440 `--quotas=0` runs of `greedy@sensible` (three seed sets of 480, replayed by an offline model of the simulator that matched Godot's seed-1 runs exactly): shift 1 passes 97.8%, shift 2 95.5% (held at one over shift 1), shifts 3 to 8 fail about 14% each, and 37.5% of runs are won. The overtime coin went to €923 (section 7.1).
  - **Result** (480 runs per strategy on the fresh profile, seed 1, the final v0.27 data): greedy 36.7%, skip 9.6% (27.1 points under: the gate item passes), random 2.1%. The viability bar is ⅔ × 36.7 = 24.5%, with the target build fitting at least 60% of final decks: Breakfast special 31.3% / 83.5%, Bulk buyer 27.1% / 61.5%, Clearance collector 30.4% / 70.2% and Mixed basket 39.8% / 98.1% are viable, so 4 of 5 pass. Coupon specialist is not (17.3% / 97.5%): its deck holds 4 or more coupons for one coupon slot, and Extra coupon slot is rarely worth taking (21 of its 480 runs). The 40% bar warns: Coupon specialist is the main build of 40.3% of greedy's won runs, because 2 coupons already fit it. The coupon-slot duel has no dominant coupon (top shares: Opening deal 45%, Repeat 39%, Multipack 33.5%); Breakfast sticker, Shelf swap and Clearance tag are never the best in the starting-deck hands (5.6 to 6.4 under the average), Final markdown 4.5 under. Inspections fail 11–16% each. Shifts 2 to 8 pass 90% with Eggs in hand against 68% without (90% / 66% on v0.26) and 88% / 79% with Milk (90% / 64%): Eggs is still the largest single point of failure. Big basket is still almost never picked (8 of 480 runs). No card is dominated. A later offer on the fresh profile shows one of Clearance collector's cards 44% of the time (15% before) and one of Breakfast special's 60% (66%).
  - **List gate** (`--list-gate`, 240 runs per state, `greedy@sensible`): fails, 10 of 27 states pass (fresh profile 35.0%). Lists holding Cold cases win 23–30% (all 8 such states fail), lists of two new aisles 22–27%, the first list Pantry + Household 42.1%; without Household listed, Clearance collector's key-card chance falls to 73–79% of the fresh profile's (Breakfast special 84% on Cold cases + Household). The developer stopped the balance passes here (2026-10-11): list-specific tuning is left to the playtest rounds, which watch these list states.

It doesn't measure fun, only what is possible. Quotas are set so that a sensible but not optimal order passes.

## 9. Testing and quality

- Unit tests: every rule, every coupon, every upgrade and inspection, the run stock, save and resume, seed reproducibility
- Data tests: the aisle rules (section 7.2)
- Golden tests: fixed rows with known totals (the doc's 31 / 18 example stays forever)
- Playtest rounds: end of phase 1, middle of phase 2, end of phase 3, phase 4. They replace the prototype's outside playtest
- The end-of-phase-1 round also asks the prototype gate's questions: can players explain a payout and their order, find a coupon combination on their own, and restart voluntarily? It also times two back-to-back runs (non-interactive reward and upgrade time about 15 s or less per run, the sum of `armed_ms` over the run's offers; fewer than about 70% of second-run presentations skipped), checks that people can name each upgrade's condition line, and asks whether players still want the impulse rack on their third restart
- The middle-of-phase-2 round (decided with the user in v0.27, issue #42): the developer plays first, then 2–4 friends play the web build (`fb-p2`) and each sends one exported log, summarised by `tools/log_summary.py`. It asks every question of the end-of-phase-1 round, which never ran. It covers the fresh profile only: capsule items can't be unlocked until the phase 3 machines exist, and no debug unlock is added
- Keep a list of the 3 problems that most affect understanding or fun; update it daily
- Middle-of-phase-2 round (`fb-p2`, the developer and friends, reported 2026-10-12). The idea went down well. The 3 problems:
  1. Without art, effects and final sound the game is hard to read and to enjoy (phase 3: the art issues and the count-up)
  2. The sound isn't pleasant, especially the counting sound: one placeholder sample pitched up to 3×. Fixed by the count-up's scale notes and the generated per-pitch notes (section 6.2), and by CC0 recordings for every sound (section 6.3)
  3. Players first thought they had to ring up the **lowest** total, as if saving the customer money. The game needs to say early why a higher total is good (the developer's idea: a premium supermarket whose rich customers want to spend more). This affects understanding, so it must not depend on a cut-list feature such as the run intro

## 10. Risks and what gets cut

| Risk | Response |
|---|---|
| Art takes longer than planned | Fewer unique packaging designs (reuse frames + icons) · simpler background · cut PNG export · an undrawn item never blocks content: a product shows the 48x48 art-pending box with its name printed in it, a coupon the real slip with its name (#75, section 6.1), so items can ship before their art |
| Coupons create one dominant combination | Simulator + limits (max coupons per row, coupon slot count, Repeat can't copy amplified values) |
| Upgrades feel weak or samey | Fewer upgrades (6) that are more distinct, rather than 8 average ones |
| Too many ceremonies for the presentation hours | The count-up, the dessert and the final receipt come first; the kiosk ceremony, run intro and capsule-machine animation are cut before them (cut order below) |
| Players skip reward and upgrade presentations | Measure `presentation_skipped`; shorten until second-run skips are under about 70% |
| Item count multiplies art (about 30 more products) | One sprite per item, reused as the figurine · cut the machine-opened aisles whole, with their machines, before any base product; the stock rule works with any number of aisles |
| The capsule machines read as monetisation | 1 coin = 1 capsule, no shop, nothing for sale; never called "gacha"; the store page states there are no microtransactions |
| The shopping list adds friction at run start | Hidden until the budget is passed, pre-filled, one click, "Surprise me". If over about 70% of lists are never changed, make "Surprise me" the default |
| One list dominates | Simulator list gate · `run_start` logs the aisles and stock size · win rate per list in the summary script |
| The first list feels like losing an aisle | The stock gets denser, not weaker; the first list is pre-filled (section 7.2: the new aisle if there is one) and new arrivals always show up |
| Schedule slips | Cut in this order: kiosk ceremony → PNG export → run intro → capsule-machine animation (a plain machine panel stays) → shopping-list note (a seeded random list stays) → 3rd inspection → machine-opened aisles, whole, with their machines (retune the coin amounts for the 7 capsules left in the base machines) → upgrade count. Coins and saved unlocks are cut only after all of these. **Never cut:** the scoring explanation, the counting presentation (including the dessert), bug-fixing time. |
| Confusing rules | Simplify effects before adding content |

Content freeze at the end of phase 3. No new features after that.
