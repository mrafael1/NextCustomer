# Next Customer: Full Build Plan

> Status: draft v0.60. **This plan will change.** Each full-build playtest round (section 9) can rewrite parts of it. Update the changelog when it does.
> The prototype (`docs/PROTOTYPE_PLAN.md`) closed at proto-r1. Its outside playtest and decision gate (section 9 there) were not run; their questions move to the full build's playtest rounds (section 9).
> Engine: Godot 4 (exact version pinned in `AGENTS.md`), GDScript with static typing. Platform: Windows, mouse. Steam is the main store; itch.io hosts a web demo.

## 1. Pillars

Every feature must support at least one of these. If it doesn't, it waits.

1. **Coupons are the fun multiplier.** They create combinations that are impossible without them, and they bend the rules, not only the numbers.
2. **Scoring is readable.** It is deterministic and every payout is explained. The result can be ridiculous, but the logic is always clear. Every item's price and effect is on its ticket on the belt's price rail, or one scan away on the monitor and the receipt: scanning an item (resting the pointer on it) shows its full rule and, on the belt, every line it adds to the receipt. The hand shows art only.
3. **Counting points feels great.** The receipt, the printer and the climbing total are the main reward.
4. **The art has a strong identity.** A warm supermarket checkout seen from just above the counter (one camera), with arcade warmth, in pixel art: chunky shapes, bold outlines, brushed steel, warm wood, teal fittings and cream paper, with the store's sections behind a soft haze (mock-up B2, #80, section 6.1). Velvet and brass survive only on the CLOSED stanchions and in the monitor's gold LED (its brass bezel, captions and quota line, velvet-dark unlit segments, and the COUPON kind on a scan). The 1990s discount supermarket of v0.17 gave way to the boutique of style frame v2 on 2026-10-14, and the boutique to B2 on 2026-10-16.

Pillar 2 also covers choosing: every item the player can score shows its ticket, an offered item its ticket too, and its rule is one scan away. A basket item shows its art only and its price and rule on the monitor when scanned (#80). A view without rules (item sprites only, as on the figurine shelf or the back wall's stock) is a catalogue, never an item in the row.

Rules:
- Products, coupons, upgrades and inspections are **all made of the same rule hooks** (upgrades through `UpgradeRule`, which has the same hook names as `Rule` and is asked about every slot by the scoring loop; `docs/PROTOTYPE_PLAN.md` section 3.8). A new idea is a new rule script plus a data file, never a change to the scoring code.
- `score()` stays a pure function. All presentation plays back `ScoreResult.steps`.
- Save files include a format version from the first save. The profile save (decided with the user, phase 1) is `profile.json` in `user://`, `format_version` 2 since #63 (the capsule seed as a decimal string, "" until the first draw, and the draw count; a version 1 profile still reads, with no seed and 0 draws): JSON (it never runs code, unlike a resource file loaded from `user://`), written to a temporary file and then moved over the save. A profile that can't be read (bad JSON, a missing or newer format version, a field of the wrong type) is reported, kept as `profile.json.bad` (then `.bad.2`, …: a backup is never overwritten), and replaced by a fresh profile. A save that can't be opened or backed up is kept as it is and never saved over in that session; a failed write leaves the save unchanged. The run save (decided with the user, phase 1; `RunSave` in `core/`) is `run.json` next to the profile, a snapshot rather than a replay, with `format_version` 5 (1 until #77, v0.41; 2 until v0.47, with the Regular levels; 3 until v0.49, before the dealt starting deck; 4 until v0.56, scored before the Banana chain). Only the current format is read, plus version 4: the older promise to read older versions went with #77, so a version 1 save (a run in progress on `fb-p2`) or a version 2 or 3 one is backed up as `run.json.bad` and a new run starts. Version 4 has the same saved form and is read because v0.56 changed scoring (#106): after its checkout the row scores again by today's rules, so a row with a Banana after a Banana can total otherwise; the record's total stands and the total check is skipped (saved again, it is version 5). Retired content (v0.56) reads as inert stand-ins: a retired register leaves the run's registers, its pick no longer uses a loyalty box (`RewardMachine.registers_picked`), and a restored pick no longer offers it. It holds what rebuilds the run (the seed, the listed aisle ids, the stock's card ids, `list_skipped` and the new arrivals; `run_start` logs the same) and the whole state: the starting deck (its id and, since v0.49, the cards it was dealt, so a recipe deck resumes with the same deal), the deck's cards with their instance ids, the next instance id, the hand (with any debug-added card), the draw pile, the row in order, the redraws used and allowed, the shift, the phase, the next inspection, the machine (`RewardMachine.to_dictionary`: the first-draw flags, the visit queue and the current visit with whether it is BOOSTED and its prizes in reveal order; a BOOSTED visit after a shift that isn't in `boosted_shifts` is a state the game can't reach), the upgrades in pick order, the inspections, the history and the run RNG's state, plus the telemetry's `run_id` and the played time (`run_ms`). The seed and the RNG state are decimal strings, because JSON numbers lose precision above 2^53. Ids resolve through a `ContentLookup` (`data/<kind>/<id>.tres`, whose id must match the file name), and the stock comes from its saved ids, so a resume never depends on a profile that changed after the run started. Content a rule change removed (since v0.56: the Extra coupon slot upgrade and the Coupon slot closed inspection, `ContentLookup.RETIRED_UPGRADES` and `RETIRED_INSPECTIONS`) still resolves, to an inert stand-in with its id and name and no effect, so an older save resumes without an error: a retired register is dropped from the run's registers (the history keeps its pick, and its machine visit reads as before), a retired inspection stays on its shift with no effect (so the shift keeps its bonus ticket), and a planning row longer than the shift's slots (Extra coupon slot's last card) gives its last cards back to the hand. This needs no new format version of its own. A resumed run continues exactly as if it had never stopped: the same draws, redraws, machine prizes and inspections. It is written at every stable point (the save points `planning`, `machine`, `machine_pick` and `scored`, #77): every shift's start, every place, remove and redraw, the checkout click (MACHINE_CHOOSE: closing the game during the count-up resumes on the machine with its chutes lit; the profile of a run that ends is saved at the same click), after a chute's draw (MACHINE_PICK, with the RNG state after the draw and the first-draw flags spent, so a resume shows the same prizes revealed with no replay), after each pick or bin that another visit follows (MACHINE_CHOOSE for a BONUS visit, MACHINE_PICK for STAMP DAY, drawn first), and at the shift's last pick or bin (SCORED: a resume goes straight into the next shift). Never mid-animation, and never a picked-up card, a redraw selection or the deck-full chooser (the prizes show again, armed). A checkout that ends the run deletes it. A run save that can't be read gets the profile's treatment, with its own numbering (`run.json.bad`, `.bad.2`, …): bad JSON, a missing or other format version, a field of the wrong type, an id that no longer resolves, or a state the game can't reach (a shift outside the run, another phase, a history that doesn't fit the shift, a row card not in the hand, a draw-pile card not in the deck, a repeated instance id, …); a new run then starts and overwrites it at its first save point. Deleting it also removes a leftover temporary file. The title screen reads it without reporting or backing anything up: with a readable save it shows Continue (shift N / M) and New run, and a background click starts nothing (Enter or Space continues); New run asks first ("Abandon the run in progress? It won't count."), then deletes the save and starts a new run. An abandoned run records nothing in the profile, like a restart before the end. The shift screen resumes the save when it holds a readable run and starts a new run otherwise. Telemetry: `run_resume` and `run_abandon` (`docs/PROTOTYPE_PLAN.md` section 8), and `run_end`'s `run_ms` counts played time only.
- The stock is built before `RunState` and passed in. It is ordered staples → listed aisles (aisle data order) → new arrivals → `coupon_pool`, each in data order, never by unlock order. Unlock recency ("newest first", section 7.2) only decides which new arrivals get in, not where they sit. The stored stock ids make replay independent of the profile.
- Derived streams (the run's list until #65, `surprise_list`; each capsule draw, `capsule_<draws>` of the profile's capsule seed, #63; the impulse rack's `impulse_rack` stream until #77) are separate `RandomNumberGenerator` instances seeded from `hash([run_seed, "<stream name>"])`, created by the caller outside `core/` (`EventLogService.derived_stream`, next to the run seeds) and passed in, so `core/` still never makes a seed. The machine's draws use the run's RNG (at the chute's choice, not at the checkout), and its odds use no RNG.
- `CardDefinition.art_ref` stays a path; presentation loads the sprite, so `core/` stays free of art. Since #75 every item is 48x48 art at 2x: a product's `art_ref` names its sprite (`art/items_v2/`), a coupon's names the icon drawn on the shared slip, and an empty `art_ref` shows the art-pending box (section 10).
- `CardDefinition.sticker_text` (#75) is the price sticker's short effect, a template with no digits ("+{bonus_each} per earlier {tag}"). `core/card_text.gd` (`CardText`) fills in its numbers, tags and names from the card's own rule (`sticker_summary()`), so the sticker never drifts from the rule; a variant with no template of its own uses its base card's. Bread and Potatoes have none: their sticker shows only the price.
- Aisles reference cards; cards stay flat in `data/cards/`.
- Any summary of a result (for example coupon credit) is computed and tested in `core/`, and only after its attribution rule is agreed.
- Tests run headless in CI (GdUnit4 GitHub Action) on every push.

## 5. Design frameworks

### 5.1 Coupons (the core)

Coupons fall into four types. 1.0 has at least 2 of each type, except Connector (at least 1, a second only if adjacency payoffs justify it).

| Type | What it does | Examples |
|---|---|---|
| **Connector** | Creates adjacency between products that are not neighbours | Shelf swap (the next product also counts as just after the row's first product; built in phase 2, v0.20) |
| **Relabeller** | Changes tags | Breakfast sticker, Clearance tag (the next product gains Clearance; built in phase 2, v0.23), Organic label (the next product gains Produce; held: every Produce reader is in Fruit & veg, so it would do nothing in a fresh profile or in lists without that aisle, v0.25) |
| **Amplifier** | Multiplies or copies | Repeat, Multipack, 2 for 1 (same product on both sides: the second one pays ×2; it fizzles otherwise, and two in a row both fizzle) |
| **Position** | Rewards placement | Final markdown, Opening deal (if in the first slot, the next product pays ×5, ×3 until v0.27; built in phase 2, v0.23) |

**Slots (decided; any card in any slot since v0.56, #106):** 7 general slots. A row holds at most `slot_count` cards (7), of any kind; upgrades and inspections that add or remove a slot change that number for the run or the shift (Big basket +1, Short belt −1). Coupons in the row still break adjacency, so every positional coupon keeps its meaning and `score()` doesn't change. Every row that was legal before stays legal. Content naming slot positions reads the same: Opening deal's first slot and the last-slot cards (Final markdown, Batteries, Stale doughnut) are the row's first and last filled slots; Shelf swap and the Breakfast sticker name the next slot; Slot engine doubles the card in slot 6, whatever Big basket or Short belt do to the row's slots (since v0.57, decided with the user on 2026-10-24; v0.56 kept the 6th product, the 7th with Big basket and the 5th on a Short belt shift), and slot 6 wears its talker on the belt (section 6.2); its tuning is for the final balance pass. Until v0.56 the row had 6 shared slots + 1 coupon-only slot: at most `slot_count` products (6) and at most `slot_count + coupon_slot_count` cards (7), one coupon in the coupon slot and extra coupons in product slots; `coupon_slot_count`, Extra coupon slot and Coupon slot closed are gone.

Good coupon rules:
- It creates a combination that **did not exist** without it, or it changes the best order of the row.
- Its effect fits in one line of rule text and one icon, and its price sticker's summary in two short lines (`sticker_text`).
- It has a cost: it uses a slot, or it only works in a certain position.
- It is not dominated: the simulator finds hands where removing it lowers the best score. (The prototype Bundle failed this: it only repaired the gap its own slot made.)
- No loops: a copy never triggers effects again, and coupons cannot copy coupons.

### 5.2 Register upgrades (designed carefully)

Upgrades last for the whole run. They live on the **loyalty card**: it starts empty (a starting deck's upgrade comes pre-stamped in a box of its own before the machine's boxes, section 7.3), each upgrade stamps one box and shows its perk icon, and the upgrade's receipt lines and count-up fly-ins come from that box. Since #77 (v0.41, decided with the user on 2026-10-20) they come from the RECEIPT REWARDS machine's **REGISTER** chute ("STAMP YOUR CARD", section 5.4) on any visit after a passed shift, instead of the exit kiosk after the shifts in `upgrade_shifts` (2, 4 and 6), which went with that field (#66 and #56's kiosk question closed into #77). Like the kiosk, the machine sells nothing and is a separate prop from the capsule machines (section 7.1).
- **Tiers:** each upgrade in `upgrade_pool` has a rarity in `data/balance/machine.tres`: Coupon engine and Category engine are RARE, Slot engine LEGENDARY, the others COMMON. Slot engine moves to RARE if Breakfast special fails the viability check (section 8; TODO(S2): the balance runs' verdict). REGISTER's odds follow the run's progress like any chute's (section 5.4), and REGISTER is lit only on BOOSTED visits and STAMP DAY (v0.47).
- **The cap:** the card holds `register_cap` (3) machine registers. At the cap the REGISTER key reads CARD FULL and draws nothing. A starting deck's upgrade has a box of its own and never counts, so the loyalty card shows `register_cap` boxes, plus one for a starting upgrade.
- **The draw:** up to 3 stamp tickets, of 3 different types, never an owned upgrade (an owned register never drops again), and one that fits the deck (its builds, `docs/PROTOTYPE_PLAN.md` section 3.8) while one is unowned: "one fits your cart". A REGISTER visit can't be binned: the player picks one. Since v0.49 the starting deck is dealt per run (section 7.2), and a dealt deck usually fits a build from the start: on a new profile about 97 % of deals fit Mixed basket (6 different tags) and about 56 % Clearance collector (2 Clearance cards), while the fixed starter fits none (a probe of 500 seeds; `tests/core/starting_deck_test.gd` pins the rates over 200). So "one fits your cart" is almost always met by a Mixed basket upgrade from the first REGISTER or STAMP DAY visit, rather than following what the player drafts. The builds' thresholds were set on the fixed starter deck; raising Mixed basket's and Clearance collector's, or not counting the starting cards, is for the user to decide (TODO(S2): with the final balance pass, where `build:mixed_basket`'s "fitting at least about 60 % of final decks" means little under `--random-start`).
- **STAMP DAY** (the floor): after the shifts in `stamp_day_shifts` (2, 4 and 6), a run that holds fewer machine registers than that shift's `stamp_day_floor` (1, 2 and 3) and whose card isn't full gets a free REGISTER visit after its other visits: drawn at the shift's odds level (section 5.4), no chute to choose and no bin; STAMP DAY is neither Normal nor BOOSTED and keeps its own stamp. A run that never chooses REGISTER still owns 1, 2 and 3 registers by those shifts, as the kiosk gave them.
- **When they act:** a register taken on a visit acts from the next shift's start (`ShiftLimits` reads the upgrades there): a Big basket taken after a shift changes nothing in the shift just scored.

Good upgrades:
1. **Change what you draft or how you order cards.** A flat "+N to everything" is not allowed.
2. **Push towards a build without making it mandatory.** Each upgrade states which build it supports.
3. **Have a tradeoff or a condition.** For example "the first coupon in the row pays ×2", but only the first one, and only if it pays something (`docs/PROTOTYPE_PLAN.md` section 3.8).
4. **Use the existing hooks.** If an upgrade needs a new hook, it is a design flag to discuss.
5. **Are visible:** stamped on the loyalty card and named in the receipt explanation.

| Type | Example |
|---|---|
| Rule bender | Coupons no longer break adjacency (out of the pool since v0.27: it never raised a best row) |
| Slot engine | The card in slot 6 ×2, any card, with any number of slots (since v0.57; until then the 6th product, coupons not counted, which from v0.27 followed the shift's slots: the 5th on a Short belt shift, the 7th with Big basket; until v0.56 the last regular product slot) |
| Category engine | +3 per category present when the last product is scanned |
| Coupon engine | The first coupon's payout ×2 |
| Economy | +1 redraw per shift (a redraw replaces one basket since v0.45, `docs/PROTOTYPE_PLAN.md` 3.8; "+1 card drawn" was cut in v0.21: it overlapped the redraw; +1 coupon slot was removed in v0.56) |
| Risky | Big basket: one extra slot (no quota raise since v0.56, #106; it was +15%) |

Upgrade offers: 3 options, from different types, at least one fitting the current deck (since v0.21: builds are data files measured from the deck, `docs/PROTOTYPE_PLAN.md` section 3.8). The player must pick one: there is no skip. Every ticket shows the same fields in the same order: name, type, effect, condition (its own line), supported builds. Since #77 the offer is the REGISTER chute's draw (above), whose stamp tickets show these fields on their hover card (`UpgradeTicket.field_texts`).

### 5.3 Inspections
Visible restrictions that test a build. One is announced before the previous shift's reward choice, printed as a red notice on the receipt under the total (before the machine visit, #77). A passed inspected shift earns the BONUS ticket (section 5.4), and its receipt gets an INSPECTION PASSED stamp. Inspections never go on the loyalty card. Never disable several parts of a build at once. Start with 3 of: only 5 product slots · the 3rd product pays 0 · duplicate payouts capped at 4 · the coupon slot is closed.

Phase 1 (decided, `docs/PROTOTYPE_PLAN.md` section 3.9): shifts 3, 5 and 7 are inspected, each with an inspection drawn from the pool with the run's RNG at the previous passed checkout. The placeholder is "the 3rd product pays 0", which behaves like Soup beside Frozen. During the shift, a red tag in the top bar shows it.

Phase 2 (decided, v0.22): the 3 were Spot check ("the 3rd product pays 0"), Short belt (one slot fewer than the run has, so Big basket keeps 7; one product slot until v0.56) and Coupon slot closed (one coupon slot fewer; removed in v0.56 with the coupon-only slot, so 2 remain), never the same one twice in a row. From v0.27 (issue #42) to v0.56 Short belt moved Slot engine to the 5th product instead of turning it off, which had disabled a slot and an upgrade at once; since v0.57 Slot engine keeps to slot 6 whatever Short belt does (section 5.2). "Duplicate payouts capped at 4" was rejected: it disables several parts of Bulk buyer at once. A closed slot shows as a CLOSED panel on the row.

### 5.4 The RECEIPT REWARDS machine (#77)

Decided with the user on 2026-10-20 (design files in `docs/art/mockups/machine_77_src/`: `DECIDE_77.md`, `BRIEF.md`, `BALANCE.md` and the draw, `flow/draw77.js`; the approved look is look F, "RESTOCK HATCH", `docs/art/mockups/machine_77_flow.html`). After every passed shift but the last, the shift's receipt feeds into one cabinet beside the belt. It replaces the impulse rack, the reward print-out and the exit kiosk. Its rules data is one file, `data/balance/machine.tres` (`MachineDefinition`, referenced from `BalanceDefinition.machine`); `core/reward_machine.gd` (`RewardMachine`, held as `RunState.machine`) runs it, and the UI only displays its state (`RewardMachine.chute_info` and its `MachineOddsCard`).

- **Chutes:** four keys, one prize kind each. **NEW ITEMS** ("ADD TO CART"): the stocked products (section 7.2). **COUPONS** ("ADD TO CART"): `coupon_pool`. **REGISTER** ("STAMP YOUR CARD"): register upgrades (section 5.2). **UPGRADES** ("IMPROVE ONE YOU OWN"): item upgrades (below), and "NOTHING TO IMPROVE" when no copy can step. A chute that can't draw is never lit, and colour is never its only sign (the padlock, CARD FULL's stamps).
- **Two machine states (v0.47, decided with the user on 2026-10-22):** a **Normal** visit lights NEW ITEMS and COUPONS (both binnable); a **BOOSTED** visit lights REGISTER and UPGRADES. The ticket visit after the shifts in `boosted_shifts` (3, 5 and 7, explicit data in `machine.tres`) is BOOSTED, and since v0.53 so is the BONUS visit after it (decided with the user on 2026-10-23 after playing; by the same rule, from the state after the ticket's pick); every other ticket visit and BONUS visit is Normal, and STAMP DAY is unchanged. All four keys stay on the machine; an unlit key is padlocked like a closed one ("NORMAL VISITS ONLY" on NEW ITEMS and COUPONS during a BOOSTED visit; "BOOSTED AFTER SHIFT n" or "BOOSTED VISITS ONLY" on REGISTER and UPGRADES during a Normal one). A BOOSTED visit is marked in the machine's own language: the head plate's "BOOSTED!" stamp (landing as the keys light, with `stamp_notice`), the display's "· BOOSTED VISIT" after the receipt read's quota (in the passed inspection's place, which the BONUS visit names), and its sub-line. If REGISTER is full (or nothing fits) and UPGRADES has nothing to improve, the visit (a ticket or, since v0.53, a BONUS visit) falls back to Normal, and its REGISTER and UPGRADES keys say why ("CARD FULL", "NOTHING TO IMPROVE") instead of when the next boost comes; if only one of them can draw, only that one is lit (`RewardMachine.lit_chutes`, `is_boosted`). A visit none of whose lit chutes can draw (no products and no coupons to draw, which live data never gives) is skipped, and the next queued visit starts.
- **A visit:** the player hovers or clicks a key to read its odds card, confirms one chute, and the machine draws its prizes with the run's RNG at that moment (not at the checkout, so old seeds no longer replay old runs). Up to `prizes_per_visit` (3) prize tickets ride out of the stockroom and open rarest last; the player picks one, or bins NEW ITEMS and COUPONS ("BIN IT ✕"; REGISTER and UPGRADES must pick). A pick that adds a card at the deck limit opens the deck-full chooser, whose cancel returns to the prizes.
- **Rarity:** every prize is COMMON, RARE! or LEGENDARY!!, from the rarity lists in `machine.tres` (anything not listed is COMMON). Products follow `docs/art/mockups/machine_77_src/product_rarity.json`, with Tea bags and Carrier bag RARE (R3b, decided); Lemon, Iced bun and Squashed cake are LEGENDARY. Repeat, 2 for 1 and Multipack are RARE coupons, Opening deal LEGENDARY. The fresh stock holds no LEGENDARY product, and its odds card says so (decided with the user: kept).
- **Odds per level** (integer weights per drop, COMMON / RARE / LEGENDARY; the live values, TODO(S2): confirm or replace with the balance runs' values): level 0 75 / 22 / 3, level 1 65 / 28 / 7, level 2 55 / 33 / 12, level 3 45 / 37 / 18 with the first drop at least RARE ("1 of 3 at least RARE").
- **Odds by progress (v0.47):** every visit after a shift (ticket, BONUS and STAMP DAY) draws at that shift's odds level, `shift_odds_levels` in `machine.tres`: after shifts 1–2 level 0, 3–4 level 1, 5–6 level 2, 7 level 3. The odds card shows the current odds. Until v0.47 each chute had a Regular meter ("REGULAR n/3", 0 at a run's start, a punched hole per pick or bin that a later visit could use) and the odds card showed the next visit's odds; the meter, its punch and its sound are gone, from the screen and the rules.
- **Guarantees,** swapped in inside the rolled tier: NEW ITEMS holds a stocked `generally_useful` product (since v0.49 the set prefers, in each rarity tier, the products the deck holds no copy of, a BIG or GOLDEN copy counting as its plain card; a tier whose useful products are all in the deck keeps them all, so every tier that could swap one in still can); the run's first COUPONS draw holds a coupon from `first_offer_pool`; REGISTER holds an unowned upgrade that fits the deck; UPGRADES has none. If no drop holds one, the last drop whose tier has one left is swapped for it; if none can be, the guarantee is skipped for that visit. **New arrivals:** the run's first NEW ITEMS draw holds the stock's newest new arrival (`new_arrival_first_visit`) at its own rarity, so it may lift or lower that drop's tier, and its ticket wears a NEW tag (decided with the user, Q4; it replaces the rack's "the newest new arrival takes a slot", section 7.2). Guarantees may lift a tier (the level-3 floor and REGISTER's types can too); the odds card shows the true result.
- **Empty-tier fallback:** a rolled rarity with nothing left to draw steps down a tier, then up; with nothing at all the draw ends short ("PICK 1 · ONLY n IN STOCK"). A prize never shows twice in one draw, and REGISTER never shows a type twice.
- **The odds card is exact:** `MachineOdds` enumerates the same draw process `MachineDraw` runs (no sampling, no RNG): each rarity's share per drop, each prize's chance to be in the draw (grouped by equal odds, guaranteed names in bold), the guarantee lines, the fallback notes ("LEGENDARY: none in your stock · rolls fall to RARE", "CART FULL: SWAP 1 OUT", a short draw), P(at least 1 RARE or better) and P(at least 1 LEGENDARY). Tests check it against the draw's frequencies and against fixtures generated from `draw77.js`.
- **The BONUS ticket:** a passed inspected shift (`bonus_after_inspection`; also the shifts in `bonus_extra_shifts`, none in live data) earns a second full visit after the first pick: "BONUS TICKET!", from the state after the first pick (the cart holds its prize, an owned register no longer drops). Until v0.53 a BONUS visit was always Normal (v0.47: NEW ITEMS or COUPONS); since v0.53 (decided with the user on 2026-10-23) the BONUS visit after a boosted shift (3, 5 and 7, the inspected ones) is BOOSTED too, LOYALTY and UPGRADES, with the BOOSTED visit's fallback (neither can draw: Normal; one: only it), and the machine stays PREMIUM through both visits; after any other shift (a `bonus_extra_shifts` shift) it is Normal. The loyalty cap (3) is unchanged, so two LOYALTY picks on one shift can fill the card sooner. A shift's visits run ticket → BONUS → STAMP DAY; live data never puts BONUS and STAMP DAY on one shift (a data test).
- **Item tiers:** an UPGRADES prize steps up copies of a product that has a chain in `data/item_upgrades/` (since v0.48 all 20 products a new profile stocks: the 6 staples and the 14 base aisle items; since v0.52 also the 30 capsule products, #89, built on the same rule while the user was away, numbers to be confirmed; until then they stayed plain, decided with the user on 2026-10-22): plain → **BIG** → **GOLDEN**. COMMON steps one copy (the highest tier below GOLDEN) up once, RARE takes a plain copy straight to GOLDEN, and LEGENDARY is SHELF UPGRADE: every copy below GOLDEN steps up once (it needs `shelf_min_copies`, 2, copies that can step). A tier is a card of its own (`data/cards/<product>_big.tres` and `_golden.tres`, `CardDefinition.tier`) and a variant of its plain card, so it counts as its base everywhere (the Banana chain, 2 for 1, rules that name a card, builds, "win with X"). The deck's copy is replaced by a new instance with the same instance id (`Deck.upgrade`); the checked-out row keeps the old one. The tiers' numbers are in `docs/PROTOTYPE_PLAN.md` section 5 and follow one tier rule (v0.48, from the starter chains): BIG adds +2 to the base and keeps the rule; GOLDEN keeps BIG's base and doubles the bonus (a charged multiplier gains 1 charge instead, a bonus that is the base counts twice); a card with no bonus (Bread, Soup, Potatoes) adds +2 to the base at each step. Carrier bag's GOLDEN is set by hand (+7 per earlier Food, not +10); Dented can and Flickering bulb have no downside in the data, so the rule applies to them unchanged. `tests/data/item_tiers_test.gd` holds every chain to the rule and its one exception (placeholders; TODO(S2): the balance runs' values and the GOLDEN Milk nerf, which the user decides with them). Tiers are never stocked or unlocked, and their items wear a BIG or GOLDEN tag.
- **The premium machine (v0.50, decided with the user on 2026-10-23; mock-up `docs/art/mockups/premium_machine_v1.html`, its stills and `premium_machine_v1_src/`):** the machine is redrawn front-on with 1 px ink outlines (`ui/machine/`: `MachineCabinet`, `StockWindow`, `MachineTray`, `PrizeRow`, `MachineArt`, `MachineLook`), and the camera's crop keeps the whole cabinet in view. A Normal visit is the **CLASSIC** face, "RECEIPT REWARDS" with the NEW ITEMS and COUPONS keys. A BOOSTED visit (after shifts 3, 5 and 7) is the **PREMIUM** face, dressing A: a dark night sign with gold "PREMIUM REWARDS" and chasing bulbs, a 3 px gold trim, a gold receipt stub in the slot, gold pedestals, tray and keys on the teal body, and the LOYALTY and UPGRADES keys (dressings B and C are not built). The turn from classic to premium is its own beat after the receipt is read (`premium_ms`, `premium_rm_ms` under reduced motion), and the machine stays premium for the whole visit; since v0.53 the BOOSTED BONUS visit after it opens PREMIUM (`MachinePlan.premium_held`: no second transform, no snap back to classic; a BONUS visit BOOSTED after a Normal ticket visit turns PREMIUM after its own read), and STAMP DAY lights its loyalty pair on the classic face. The visit is **announced the shift before**: the monitor prints the announce receipt inside its screen over a dithered gold sunburst ("NEXT RECEIPT", PREMIUM between two pixel stars, LOYALTY and UPGRADES, "MEET THIS SHIFT'S QUOTA"), which then flies up to hang, on a string from the quota mark, as a gold "PREMIUM NEXT" tag (with its star) on the monitor's top bezel, clear of the brief's text, for that shift's planning and its count (`PremiumAnnounce`; `RewardMachine.boosted_if_passed` answers it; a resumed shift shows the tag without the print). Shifts 3, 5 and 7 are also inspected, so the bonus notice's pulse waits until the receipt has flown up. Before the turn to premium the classic keys stand cream and idle over their stocked windows (never padlocked), then sink. **REGISTER is called LOYALTY** wherever the player sees it (keys, stock window, tickets, CARD FULL); the enum, save and telemetry names stay `register`. The **stock window** (the vitrine) shows, per lit key, three SEALED tickets (COMMON, RARE, LEGENDARY) with each rarity's exact share from `MachineOdds` at the shift's odds level (whole percents by largest remainder, so a column adds up to 100; "<1%" for a sliver), never the prizes themselves, so nothing in it reads as a guaranteed drop (the user's note on the mock-up); an unlit key's window is dark, and hovering a key brightens its column. It replaces the odds card. Since v0.53 (the user's play review on 2026-10-23: "it feels a bit too raw") the sealed tickets are drawn crisp, through the sharp-pixel material at an integer 2x on the 2 px grid, and each share sits on an **odds plate** under its pedestal in the machine's own language: a small charcoal LED window like the display's (scanlines, a backlight in its rarity's colour, brighter on the hovered key's column) with the share in the number font (Atkinson 750) in its rarity's colour, over a tab in RarityTab's colours with its word. ### 6.3 Sound

Decided with the user in v0.30 (issue #62), after the `fb-p2` players disliked every synthesised placeholder: pleasant, soft-edged recordings that still make the count juicy.

- **Sources:** real recordings, all CC0 1.0 (no attribution; safe in the public repo, on Steam and in the web build), each licence checked on its page on 2026-10-12: Kenney's Interface, Impact and Casino packs, Freesound recordings and VCSL instrument samples (xylophone, glockenspiel, hand chimes, bell tree, marimba). Short, trimmed excerpts live in `audio/src/` (ignored by Godot), each pack's licence beside its files and the Freesound IDs in `audio/src/freesound/ledger.tsv`; `audio/src/README.md` says where each came from and how it was cut. Only the scan beep (a soft sine at C7, above the ladder) and the fizzle are synthesised. Nothing is commissioned for now
- **Build:** `tools/make_sfx.py` (Python standard library, deterministic) is the single step from `audio/src/` to `audio/sfx/`: it folds each excerpt to mono, cuts, resamples (a windowed sinc), filters, layers and fades it, and normalises each sound to its `GAINS` peak, writing mono 16-bit 44100 Hz WAVs (was 22050). Its test checks that two runs write the same bytes and that the committed files are up to date. Review time is logged per sound in `audio/src/production_log.tsv`, as for art (section 6.1)
- **The set:** 60 files with fixed names (`Sfx.SOUNDS`), the contract between the build and the game. The count-up: `scan`, `print`, `tick`, `stamp` (multipliers), `stamp_loyalty` (the upgrade ticket), `stamp_notice` (a light self-inking stamp for the inspection notice), `rattle_s` / `rattle_m` / `rattle_l` (by the rattle's size), `register_bell` (huge totals), `ding` (a glockenspiel with hand chimes), `tag`, `link`, `copy`, `fizzle`, `denied` and `armed` (a soft bell-tree shimmer under the replayed note; it goes if it feels busy). - **The note ladder:** 11 files, `bonus_00` (G4) to `bonus_10` (G6), from the VCSL xylophone. G4, C5, G5, C6 and G6 are exact samples; the other notes are shifted at most 3 semitones, and each sample's measured tuning offset is removed, so every fundamental is within ±25 cents (tested). The timbre brightens up the ladder (soft mallets pp low, soft ff in the middle, medium ff at the top, the peak rising from 0.40 to 0.52), and each note lasts about 0.9 s, so the last one rings into the pause. `Sfx.play_note` plays the file for its index, clamped to 0–10; nothing is pitched at play time. Section 6.2's levels hold: the stamp keeps its own sample over the note at −6 dB, an armed beat replays the note at −10 dB
- **Round-robin takes:** `stamp` (3), `card_place` (4), `card_pickup` (3), `card_return` (2), `ui_click` (3) and `coin` (3) are numbered takes (`stamp_1` …). `Sfx.play("<base>")` cycles them in a fixed order, one counter per sound, so a run sounds the same every time
- **Buses and ducking:** `default_bus_layout.tres` has Master, Music and SFX (it is in the resource-loading test). SFX sits at −6 dB, so coinciding sounds don't clip, and Music at −15 dB, 9 dB under SFX. Levels are bus volumes because bus effects don't run on the web build. The dessert ducks the Music bus by 24 dB (to −39 dB) over 120 ms as #60's pause before the total starts (section 6.2), so the slam lands in near-silence at least 600 ms into the duck, and the music comes back over 600 ms at the printer feed, when the machine opens (`ShiftMusic.rewards_shown`; the reward print-out until #77); on a fail it stays ducked through the fail sound, then crossfades to the results loop; a second-tap skip brings it back over 150 ms. The final receipt ducks it by 18 dB (to −33 dB) while the coins print, until one coin gap after the last coin and at least 1 s
- **Music:** two CC0 loops from OpenGameArt, with their licences and credits in `audio/music/LICENSE.md`: "Buy Something!" by Cleyton Kauffman (the normal mix, credited as he asks) on the shift screen (`audio/music/shift.ogg`), and "Urban Shop" by MintoDog on the title and results screens (`front.ogg`). The user picked both by ear on 2026-10-12; they are re-encoded once (OGG Vorbis quality 5 with a gentle 1–3 kHz dip to clear the note ladder and the beep, about 3.4 MB for both, each step recorded in `LICENSE.md`); the fallback is "headscratcher" by congusbongus (OGA-BY 4.0, with attribution and a change notice). Both are imported with loop on and loop offset 0, so a track is swapped by replacing its file only
- **Players:** the `Music` autoload (`presentation/music.gd`) is a global service. It holds playback state only (the track, a 0.8 s equal-power crossfade and the duck), never run state, plays on the Music bus, takes an injectable error reporter and ducks through `duck()` / `unduck()` (the bus volume, or the players' `volume_db` without that bus). Browsers block autoplay, so the music starts on the title's first click (a click that starts the run leaves it to the shift screen's loop); headless runs (tests, tools) load no streams. Sound effects stay in their scenes: each scene has its own `Sfx`, which warms up every sound silently when the title or the shift screen opens, so the web build never hitches mid-count
- **The machine (#77):** existing sounds only, mapped from the page's placeholders: the receipt or stub landing `tick` ×5 / ×3 then `slot_tick`; the keys lighting the ladder notes C5 D5 E5 G5 (`play_note`); CONFIRM `ui_confirm` (the push bar's since v0.53); each bay pick a ladder note and `card_place`; the belt `rattle_s`, then `tick` every 0.18 s while it moves; PACKED `stamp_1`; a lid's tape `rip`; a COMMON reveal one note and `tick`, a RARE two rising notes (E5, A5), a LEGENDARY four (C5 E5 G5 C6) and `rattle_l`; the pick `ui_click`; a NEW ITEMS or COUPONS landing `card_place`, an UPGRADES glint `ding` and G5 C6 E6; a REGISTER or STAMP DAY landing `stamp_loyalty`; the BOOSTED stamp `stamp_notice` (the meter's punch `stamp_2` until v0.47); the restock a soft `card_place`; BIN IT `ui_back`; a padlocked key `denied`; the BONUS TICKET and INSPECTION PASSED stamps `stamp_notice`, the stub's print `print`; the STAMP DAY stamp `stamp_paid`. ## 7. Unlocks: capsule machines, aisles and decks

Design rules (from the original doc): **unlocked decks have comparable starting strength**. Unlocks add options, not raw power. No permanent payout increases.

### 7.1 Capsule machines
One capsule machine per aisle at the store exit, like the coin-op toy machines that sell little figurines. 1 coin = 1 capsule: a fixed price, no shop, no second currency, nothing for sale, no microtransactions.

- **Coins** print at the bottom of the final receipt, as part of the run's dessert: more the further the run got, a little for overtime, something even for a lost run. The amounts live in balance data. Decided with the user (phase 1, `CoinPayout` in `core/`): `coins_by_shifts_passed[shifts passed]` (index 8 is a won run), plus one overtime coin per `overtime_coin_euros` of margin over quota summed over the passed shifts, at most `overtime_coin_max` (1). A run lost early pays no table coins, so losing fast doesn't farm capsules (it can still earn the overtime coin, which is very unlikely that early); a typical run pays 1, a won run 2, a great win 3. **Amounts fitted with the simulator (v0.26, issue #41, decided with the user):** the table 0, 0, 0, 0, 1, 1, 1, 1, 2 (no table coins for a run lost on shifts 1 to 4; phase 1 had shifts 1 and 2) and one overtime coin per €700 (fitted at €723 so that just over 1 run in 10 earns it, rounded down: 11% of runs; a shift-1 margin alone never reached it). On the fresh profile the sensible player's runs pay a mean of 1.18 coins, the median run 1 and a great run (p90) 3. Played as chained profiles (section 8), whose stock grows with each capsule, they unlock all 30 items in 27 runs at the median (23 at p10, 37 at p90), paying 1.05 coins a run. Keeping the phase-1 table (a run lost on shift 3 or 4 paying 1) would have paid 1.40 a run, about 21 runs, under the target. **Refitted in the balance passes (v0.27, issue #42):** the same table, and one overtime coin per €923 (fitted on 1,440 runs of the sensible player on the v0.27 data: 10% of runs earn it); a mean of 1.17 coins a run, the median run 1, a great run (p90) 2, 30 unlocks in about 26 runs. When the profile can't be saved, the results print the run's coins but no total ("you have ?"). The final receipt (section 6.2, v0.31) prints the breakdown at its bottom (shifts passed, overtime, then the coins and the profile's total), each coin clinking as the coin lines print, and the title screen shows the total.
- **The draw:** the player picks the machine; the draw inside it is random, without duplicates, until the machine is empty (that aisle's collection is complete). The first capsule from each machine is always the aisle's key item, so later items have something to combine with.
- **The TOY MACHINES' rules (#63, built in phase 3; decided with the user on 2026-10-21, `docs/art/mockups/capsule_63_src/DECIDE_63.md`):** a capsule costs `capsule_price` coins (balance data, 1). `CapsuleDraw` (`core/`) draws the key item while it is locked with no RNG use, and after that one `randi_range` among the items left. Each draw has its own derived stream, `capsule_<draws>` of the profile's capsule seed (`EventLogService.capsule_stream`): the seed is made outside `core/` the first time a profile draws, and the profile keeps it with the draw count (`capsule_seed`, saved as a decimal string, and `capsule_draws`, which starts at the unlocked item count when the seed is set; `ProfileState` `FORMAT_VERSION` 2). The profile is saved right after each draw (`CapsuleCounter`, the one place the game draws), so quitting can't reroll a capsule; a save that fails rolls the draw back in memory, reports through the save service's reporter and switches the machines off. **The draw's run index** (`ProfileState.capsule_run_index`): a draw on the results, or on the title with no saved run, comes out at the ended run's index (`run_count - 1`: "In stock from your next run"); a draw on the title while a run is saved comes out at the saved run's own index (`run_count`: "In stock after your saved run"), so the item rides the 3 runs after the saved one (default (a), not changed by the user; known edge: if that saved run is abandoned, the item misses the next run). A draw before any run has ended (debug coins only) gets −1, which the profile saves. **States:** a machine is OK, EMPTY (its collection complete), BROKE (fewer coins than the price) or OFF (the profile can't be saved: unreadable and kept, or the ended run's save failed). Telemetry: the `capsule` event (`docs/PROTOTYPE_PLAN.md` section 8). The debug panel's Profile tools give coins (+1, +5), draw from a machine (the real draw, no coin spent), unlock every capsule item and reset the collection, each saved at once.
- **The TOY MACHINES screen (#63, look A of `docs/art/mockups/capsule_63_a.html`, decided with the user on 2026-10-21):** a full-screen camera cut to the store exit (`ToyMachinesScreen`, a 1280x720 stage centred and never scaled): a hanging TOY MACHINES board, the COINS and FIGURINES n / 30 chips, the EXIT sign over the sliding doors and one globe machine per aisle (`ToyMachineView`, 144x280, `balance.aisles` order, 160 px apart from x 40; fewer machines centre left of the doors), each in its aisle's colour with its glyph and name on the sign, one capsule in the globe per item left (at most 8), a tilted "1 coin" label and a floor label ("3 of 8 left", "All 8 collected"). Picking a machine draws through `CapsuleCounter` (the coin sound, the coins chip pops as it drops, the counts change) and shows the plain reveal (`ToyReveal`, popped in with `UiKit.pop_in`): the figurine at 96x96 on a gold medallion before a sunburst (muted rays only, ending above the aisle line), NEW!, the name, the aisle's glyph and name, the stock line and OK; it arms after the results' arm delay once the mouse is up, so the draw's click never closes it, then OK, a click, Enter or Space close it. #64 animates the draw in front of this reveal. States, never by colour alone: an OK machine lifts 4 px with a pointing hand; a full machine wears an ALL COLLECTED rosette and no price; with fewer coins than the price every machine is dimmed with the arrow cursor and a notice ("No coins left. Runs that pass shift 4 pay coins on the final receipt."); when the profile can't be saved every machine is OUT OF ORDER, the coins read ?, and a notice says so; the complete collection shows the COLLECTION COMPLETE banner and "Your coins keep adding up on the final receipt."; otherwise the hint "Pick a machine: 1 coin a capsule." "Figurine shelf" opens the shelf and "Done ›" leaves. Coins can be kept; nothing nags. The copy says TOY MACHINES, capsule and figurine, never "gacha" (a test scans every string).
- **Where it opens (#63):** from the results, a "Toy machines ›" button between New run and Export log, armed with New run (clicked mid-print, it first prints the rest at once, as a tap does); the machines open over the results (under the debug panel) and Done leaves the results as they were (the receipt's coin total is the run's record and isn't reprinted). They are switched off when the ended run's profile save failed. From the title, until title B (#56) is built, a toy machine prop (the first aisle's machine at 2x) over the same button stands centre-right, clear of the centred column (a click on the prop opens the machines too, and a click between them starts nothing); the title reads the profile without reporting (an unreadable one opens the machines switched off, left for the shift screen to report and back up), a draw while a run is saved says "In stock after your saved run", the title's start keys and background click do nothing while the machines are open, and Done refreshes the coin line.
- **The figurine shelf (#63, `docs/art/mockups/capsule_63_shelf.html`, locked items hidden):** a wooden display cabinet (`FigurineShelf`) with one fixed section per aisle (two columns, `balance.aisles` order), each with its aisle sign (glyph and name), its count "n / m" and its collected figurines (the item's sprite at 48x48) standing on its plank, packed from the left in data order at a 70 px pitch. Locked items get no space, silhouette or name; an empty aisle shows "None yet", a full one an ALL COLLECTED tag, a new profile the line "Every capsule you open puts its figurine here.", and from the first figurine on (also at 30 / 30) the hint "Hover a figurine for its name." Hovering a figurine lifts it and shows a tag with its name and aisle (flipped to its left near the cabinet's right edge). Only the 30 capsule items are on it, never rules. Back returns to the machines.
- **The figurine:** the capsule holds the item's figurine, its plain card sprite. Unlocked figurines go on the shelf, which doubles as the catalogue (items without their cards).
- **Unlock unit:** an aisle's items through its machine, never orphan random cards from the whole catalogue. Unlocked items join the run's stock (section 7.2), which feeds the RECEIPT REWARDS machine's NEW ITEMS chute (the impulse rack and reward offers until #77).
- **Pacing target:** about 1 capsule per average run, 2–3 for a great run. About 30 unlocks, finished in about 25–40 runs.
- **Wording:** "capsule machine" in this plan; in-game copy may also say "toy machine". Never "gacha", in the game or on the store page.
- **Separate from the RECEIPT REWARDS machine:** the capsule machines sell figurines between runs for coins; the RECEIPT REWARDS machine (section 5.4, the exit kiosk's successor) gives the mid-run rewards and upgrades and stamps the loyalty card. They look different, sound different and do different things.
- **Phasing:** coins on the receipt and the saved unlock state in phase 1; the machine, its animation and the figurine shelf in phase 3.

### 7.2 Run stock: the shopping list
**Unlocks widen the choice between runs, never the pool inside a run.** Offers are uniform draws, so offer quality depends only on how many products are stocked. The target is about 20 products, whatever the collection size.

Each run stocks, in data order:
1. **Staples:** Banana, Bread, Milk, Eggs, Coffee and Soup, the balance data's own list (`BalanceDefinition.staples`; until v0.49 they were the starting deck's products, derived from the `DeckDefinition`; the list keeps that order, so a new profile's stock is unchanged). Always stocked, no machine. They hold 4 `generally_useful` cards (Banana, Bread, Eggs, Milk), at least 2 by a data test, so the reward guarantee always has a candidate. Aisles may add up to 2 more each. Every deck's fixed and core cards are staples (a data test; a recipe's dealt cards come from the whole stock, section 7.2).
2. **Listed aisles**, whole aisles only. If every listable aisle together holds at most `aisle_stock_budget` (16) products, all are stocked and the list is skipped (new profiles, the tutorial, the web demo, or a cut machine). Otherwise the player lists `run_aisle_picks` (2). An aisle is listable once it holds `aisle_listable_min` (4) items; the minimum applies to machine-opened aisles only, so an aisle with `base_cards` is always listable.
3. **New arrivals (the end-cap):** up to `end_cap_max` (3) items from unlisted aisles that came out of a capsule in the last `end_cap_window_runs` (3) runs, newest first. Decided with the user (phase 1): the profile keeps, in draw order, each unlocked item's run index: the 0-based index of the run at whose exit it came out (that run's count of earlier runs, not the count after it ended); a run with index N (N earlier runs) takes items with index N − 3 to N − 1, so a capsule from run K rides runs K + 1 to K + 3, newest first by run index, and within one run the later draw first. The newest is held in the run's first NEW ITEMS draw (section 5.4; until #77 it took one impulse-rack slot). A machine-opened aisle that is not yet listable reaches the run only this way: each of its items rides the end-cap for the 3 runs after it came out (decided with the user, phase 1: the window applies to every capsule item), so its early items can leave the stock before the aisle holds 4 and becomes listable. A capsule is always playable in the next run, with one known edge since #63 (coins are kept, so one visit can buy several capsules): when one visit draws more than `end_cap_max` items from unlisted aisles, the earliest of them never reaches the stock, although the reveal says "In stock from your next run" (`tests/core/run_stock_test.gd` documents it); open for the user: keep it, relax the cap for those draws, or soften the reveal's line.
4. **Coupons:** all of `coupon_pool`. Coupons are never in aisles or capsules.

Rewards draw from the stock through the RECEIPT REWARDS machine (section 5.4, #77, v0.41): NEW ITEMS draws the stocked products (plain cards only; tiers are never stocked) and COUPONS the `coupon_pool`, each prize at its rarity. **Rarity per product:** each stocked product is COMMON unless `data/balance/machine.tres` lists it as RARE or LEGENDARY (`product_rarity.json`, with Tea bags and Carrier bag RARE; Lemon, Iced bun and Squashed cake LEGENDARY), so a wider stock dilutes each product's chance inside its tier, not the tiers' odds. The guarantees carry the old offer rules over: the run's first COUPONS draw holds a combination coupon (`first_offer_pool`), every NEW ITEMS draw a stocked `generally_useful` product (since v0.49 preferring, in each rarity tier, one the deck doesn't hold yet), and a draw never shows a card twice. **New arrivals:** the run's first NEW ITEMS draw holds the newest new arrival at its own rarity, with a NEW tag on its ticket (decided with the user, #77 Q4). At the deck limit a pick removes a deck card (the deck-full chooser). **Every fresh-stock product can grow (v0.48):** the 6 staples and the 14 base aisle items each have a BIG and GOLDEN chain (section 5.4), so a new item taken from NEW ITEMS can later be stepped up by UPGRADES; tier cards stay out of every stock, deck and catalogue (a data test). Since v0.52 the 30 capsule products have chains too (#89), so an unlocked capsule product taken from NEW ITEMS can be stepped up as well (until then they stayed plain, decided with the user on 2026-10-22). **The impulse rack is cut** (#77): shift 1 starts straight away, and the first machine visit follows it. Until #77 the rack showed `impulse_rack_size` (3) stocked products before shift 1, the newest new arrival in one of its slots, and reward offers had at least 1 coupon and 1 `generally_useful` card.

**The starting deck (v0.49, decided with the user on 2026-10-22; its coupon random since v0.51, 2026-10-23):** the game's deck is a recipe, `data/decks/random_starter.tres`: 4 fixed cards, the staples every run starts with (`core_cards`: Banana ×2, Milk, Eggs), plus `random_coupon_count` (1) coupon drawn from the run's coupon pool and `random_count` (8) products drawn from the run's stock, 13 cards, with no pre-run screen (the cart reveal below shows the deal). Until v0.51 the coupon was a fixed Final markdown, the 5th core card. The coupon is drawn first, equally likely among the stock's coupons (all of `coupon_pool`, section 5.1), then the products. A product can be drawn only if it has an item-tier chain (section 5.4), so UPGRADES can grow every starting card, and is not a capsule product: the capsule products have chains since v0.52, but the recipe's `random_capsules` (a `DeckDefinition` field, off) keeps them out of the draw until the user decides (TODO(S2)), so the deal is the 20 fresh-stock products' as before, and the deck never holds more than `copy_max` (2) copies of a card, its core copies included. Each draw picks one of the products still below the limit, equally likely; a stock with too few ends the deal short. `StartingDeck.deal` (`core/`) draws on the run seed's derived stream `starting_deck` (beside `surprise_list`), after the stock is built, so the same seed and profile give the same deck and the run's own RNG draws exactly as before. **The fair-deal check (v0.54, decided with the user on 2026-10-23 after playing: "1st shift is sometimes impossible"):** after each deal, up to `fair_deal_hands` (8) hands of `hand_size` (8) are sampled from the dealt deck on the same stream (a partial Fisher-Yates each) and each is played by the sensible row player (`RowClimb`, `core/`: the simulator's `@sensible` climb, `fair_deal_changes` 3 changes from the hand order, shift 1's limits and the recipe's starting upgrade, no inspection, no redraw); the deal is kept as soon as `fair_deal_passes` (1) hand reaches shift 1's quota (the sampling stops early once it passed or can no longer pass). Otherwise the recipe is dealt again on the same stream, at most `fair_deal_redeals` (4) more times, and the deal with the most passing hands (the first on a tie) is kept. The four numbers are `DeckDefinition` fields set in `random_starter.tres` (0 hands: no check). Invisible to the player (the cart reveal shows the kept deal), deterministic by seed, the run's RNG untouched; a re-dealt deck is one the recipe can deal, so the run save's `could_deal` accepts it and a resumed run keeps it. Before v0.56 (6 shared slots + the coupon slot), on a new profile's stock (500 seeds, shift 1 at 29) 7 deals (1.4 %) were dealt again, all passed on the second deal, none fell back; since v0.56's 7 general slots every first deal passes on a new profile's stock (200 seeds), so the check no longer re-deals there (to re-check in the balance pass at the end of phase 3, TODO(S2)). The dealt deck keeps the recipe's id and lists its cards in order: the core cards, the coupon, then the products in stock order; the run save holds them (section 4; a save whose cards the recipe can't deal, such as a v0.49 deal with Final markdown among its core cards, is refused and backed up, and a new run starts), and `run_start`'s `starting_deck` logs them (no field changes). `data/decks/starter.tres` (the 13 fixed cards the game started with until v0.49) stays the fixed deck of the tests and of the simulator's `--deck`; `--random-start` plays the recipe (section 8). Nothing is written to the profile's `last_list` (the pre-fill would lock the first random list in). `RunStock.prefill_list`, the list's default described below, is built and tested in `core/` for #65, and the simulator's chained player uses it.

**The shopping list:** a note at the register before shift 1 (before the impulse rack until #77). It is pre-filled with the last list (the first time, with the newly listable aisle if there is one, otherwise the two base aisles with the most unlocked items, ties by data order), and one click clocks in. "Surprise me" picks a pair from a derived stream (section 4). The list stores a preference, never power. No per-item toggles, ban lists or figurines turned to the wall: players would prune to the strongest cards. After launch this gives way to a small capped ban list (decided with the user on 2026-10-21, #91): with progress the player may deactivate 1 item, then up to 5, and the simulator checks that the strongest ban list at each cap keeps the win rate in the list gate's band and no build over the 40% bar. Also rejected: ticketed offers (a rule change with a new hook on every rule), a seeded-only flyer as the default (kept only as the fallback if the note is cut), and a stock-size valve (the 9-item aisle cap replaces it).

**Content shape (1.0, decided; built in phase 2, v0.25, issue #35: Cold cases, Pantry and Household grow to 7 items each, and Fruit & veg, Bakery and Snacks open through their machines; `docs/PROTOTYPE_PLAN.md` section 5 lists every item; easy to change later, because the stock rule works with any number of aisles):** 6 staples · 3 base aisles open from the start (5/5/4), whose machines add 2–3 each, to about 7 · 3 aisles opened by their machines (8/8/7) · 30 capsules, about 50 products · at full collection, 15 possible lists of 20–22 products (plus up to 3 new arrivals).

**Aisle rules (data tests):** every product is a staple or in exactly one aisle · 6–9 items per complete aisle · at most 2 `generally_useful` per aisle · the capsule list starts with the key item · the staples hold at least 2 `generally_useful` products · every deck's fixed and core cards are staples · the staples alone fill a recipe's deal (their room under `copy_max` is at least `random_count`). Simulator rule: every key item and capsule item reaches the best row with a staple or its own aisle, so nothing is an orphan while it rides the end-cap.

**Saves and replay:** building the stock uses no RNG except "Surprise me". The stored stock (section 4) means a resume never depends on a profile that changed after the run started.

### 7.3 Decks and card variants (architecture now, content after launch)

The prototype already has `DeckDefinition` (id, name, cards) and data-driven cards. Phase 1 adds the remaining fields below, so adding decks and variants after that is a content task:

- `DeckDefinition`: id, name, description, card list, starting upgrade (optional), unlock condition. Since v0.49 a deck can be a recipe (`core_cards`, `random_count` or, since v0.51, `random_coupon_count` > 0, `copy_max`), dealt each run from the stock (section 7.2); the staples are no longer a deck's products but the balance data's own list
- `CardDefinition.variant_of`: card variants (e.g. "Organic Banana" as a variant of Banana), with their own optional unlock condition. A variant is a variant of a card that is not itself a variant, of the same kind (a data test)
- `ProfileState` (fields in section 4) holds the deck and variant unlocks. Saved separately from the run.
- Unlock conditions are data (`UnlockCondition`: kind, card, amount) and are checked when a run ends. No condition means available from the start. Decided with the user (phase 1):
  - **Win a run with X:** X is a card in the run's final deck, and the run must be won.
  - **Score Y in one checkout:** any checkout of the run that just ended totals at least Y.
  - **Use coupon Z N times:** across runs, every copy of Z in a checked-out row counts once. The run history records each shift's checked-out cards; earlier runs' counts come from `ProfileState`.
  - The check is pure (`UnlockCheck`, tested in phase 1). At the end of a run (won or lost), `ProfileState.record_run` checks every locked deck and variant in `data/catalogue/catalogue.tres` with the coupon counts from before the run, then adds the run's coupon uses and counts the run; the profile is saved at the checkout click. Decided with the user (phase 1): a run restarted before its end records nothing.
- **Starting upgrade (decided with the user):** a run started with a deck that has one owns it from the first shift. Upgrade offers skip it like any owned upgrade, it counts for redraws and scoring, and the loyalty card gives it a pre-stamped box of its own before the upgrade-shift boxes. The starter deck has none.

Possible ideas: Breakfast deck (start with Coffee and Milk), Coupon deck (fewer products, 2 starting coupons), Frozen deck (Frozen peas, Soup risk).
Family decks (after launch, the user's idea of 2026-10-21, #90): completing a capsule family (every capsule item of one aisle, e.g. Fruit & veg) unlocks a starting deck themed on it that holds some of its items, through a new `UnlockCondition` kind.
Card changes: unlock variants that replace a starting card (e.g. swap 1 Banana for an Organic Banana in the run start screen).

**Basket Rush (after launch):** a shopping screen that builds the starting deck. One limit: item prices in data plus a fixed basket size (a size limit alone allows 6 Eggs + 6 Milk). Dexterity never changes what ends up in the deck. It remembers the last basket, is skipped on the first run and in the web demo, and has a static mode for reduced motion. Its strength spread is checked with the simulator's run win rates.

## 8. Balance simulator

A command-line tool, run headless, that uses `core/` directly:
- For a given hand, it tries every selection and order of up to 7 cards of any kind (section 5.1; at most 6 products until v0.56), including shorter rows, because a shorter row can score higher, and finds the best possible score. That is up to about 69,000 rows for a hand of 8 (40,320 seven-card rows plus the shorter ones), and about 1.6× more when an upgrade adds a slot (Big basket; the hand of 8 caps a row at 8 cards). "+1 card drawn", which would have made it about 4×, was cut in v0.21
- It simulates thousands of seeded runs with simple drafting strategies (greedy, build-focused)
- Outputs: the distribution of best scores per shift (to set quotas), win rate per build, how often each card is in the best row (finds dominant or useless cards)
- Models the redraw (the basket redraw since v0.45, played as a player does: its row goes on the belt first, so a redraw swaps only the cards the row leaves out and never lowers the kept row; of the baskets still holding a card it redraws the one with the most cards, then the lowest total base value, then the leftmost, one-item baskets too; then it takes the row back and plays it again), the coupon slot (until v0.56; 7 general slots since), the RECEIPT REWARDS machine (#77, below; the impulse rack until then, picked with the strategy's reward rule) and a starting-deck parameter
- Reports per-shift score percentiles (used for count-up intensity) and flags dominated cards (removing them never lowers a best score)
- Values coupons against other coupons for a slot, not against skipping
- Takes a stock parameter. List gate: every legal list at full collection, plus the minimum states (a new aisle at 4 items, the first list after the budget is passed), has a run win rate within ±5 percentage points of the fresh-profile stock's, and no list pushes a build over the 40% bar. Reports the per-offer chance of seeing a build's key cards; at full collection it stays at least 85% of the fresh profile's. Since #77 that chance is read from the machine's exact odds, not sampled: the chance that a NEW ITEMS or COUPONS draw at odds level 0 on the fresh state holds one of the build's key cards (the larger of the two chutes; summed over the key cards and capped at 1, an upper bound), so `--offer-samples` is unused
- Reports coins per run from the balance-data coin amounts; they are tuned so the median run pays about 1 coin, a great run 2–3, and the 30 unlocks take about 25–40 runs (section 7.1)
- **Built in phase 2 (v0.24, issue #40), decided with the user:**
  - **Collection states.** `--profile=<save>` stocks the runs as the game would for that profile's next run (its unlocked items, run count and last list). `--collection=full` unlocks every capsule item, with no new arrivals. `--list=a+b` gives the list.
  - **List gate.** `--list-gate` plays the fresh profile and every gate state, then reports a pass or fail line for each state:
    - every legal list at full collection;
    - every list of the first state that needs one (base-aisle capsules unlocked in turn until the budget is passed);
    - each machine-opened aisle just listable at `aisle_listable_min` items, with every list that holds it.

    The gate states have no new arrivals. A state passes when, for each strategy played, its win rate is within ±5 points of the fresh profile's (inclusive, counted exactly). At full collection each build's key-card chance must also be at least 85% of the fresh profile's. A main build over the 40% bar was a failure until v0.27 and is now a warning printed beside the verdict (issue #42). A strategy with no runs on either side (the time limit) fails the state: there is nothing to compare. The gate shares `--max-minutes` between every state, so give it more time.
  - **Builds.** A build is a `data/builds/` file (section 5.2). Each run gets one **main build**: the build its final deck fits most strongly (measure ÷ `min_count`), or "no build". The **40% bar** is a main build's share of the greedy strategy's won runs; runs that fit no build count among the won runs but are never held to the bar, and the gate needs the greedy strategy. A `build:<id>` strategy drafts towards one build, to show which builds are viable (revised in v0.27, below). A build's **key cards** are the cards that count towards its measure on their own.
  - **Coins.** "A great run" is the 90th percentile of coins per run. Runs to 30 unlocks is 30 ÷ mean coins at the given stock. Chained runs, whose stock grows with each capsule, are left for the reward-economy pass once the capsule aisles exist (built in v0.26, below).
  - **Orphan check.** It samples hands of each capsule item with the staples and its own aisle, and flags an item that is never in a best row.
  - **Random start (v0.49).** `--random-start` starts each run from the game's recipe deck (`data/decks/random_starter.tres`), dealt from the run's stock on the run seed's `starting_deck` stream exactly as the game deals it (`StartingDeck`, its coupon from the coupon pool since v0.51, the fair-deal check since v0.54, against the balance data's shift 1 quota even when `--quotas` plays others, so a `--quotas=0` run deals what the game deals); without it the runs start from `--deck` (the fixed starter deck by default). The coupon duel plays the deal of the first run's seed from a new profile's stock.
  - **Run modifiers.** Already handled before this issue: every shift's row limits and redraws come from `ShiftLimits`, and the search cache keys each hand by those limits.
- **Built in phase 2 (v0.26, issue #41), decided with the user:**
  - **Sensible rows.** "A sensible but not optimal order" is a row player, not a share of the best: a strategy ending in `@sensible` (e.g. `greedy@sensible`) places the hand in draw order, then makes up to 3 changes, each the single move, swap, addition or removal that raises the preview most (`SimHillClimb`). Its redraws replace the cards its row leaves out (since v0.45 a basket of them, with the row on the belt: the one with the most such cards, then the lowest base), and after each redraw it makes up to 3 more changes from the row it kept, as a player rearranges once new cards arrive (decided with the user). The greedy valuation plays its sample hands the same way, and each shift still records the exact best row beside it: in the runs, the sensible rows reach 96% of it on average. `tools/row_calibration.sh` replays logged checkouts through both: on the 101 logged hands, an uncapped climb reached the exact best in 78% of them (98% of it on average, practically optimal), 3 changes in 45% (94% on average, 82% at p10). The logged players scored 44% of the best at the median, but against quotas of about 10, so they show no effort and can't calibrate it; the next playtest on the new curve can. A climb that starts from an empty row was rejected: it stops at two cards when every single addition lowers the total (Category engine), which no player does.
  - **Curve fitting.** No simulator choice reads the quota, so a run played with `--quotas=0` is, shift for shift, the run of any curve until its first failed shift. `--records` writes every run, and `tools/quota_fit.py` replays them under a candidate curve and coin amounts (Big basket's raise from the shift after its pick, the coins as `CoinPayout` pays them) and fits both to the targets below. It also reports, per inspection, its share of the failed inspected shifts; per upgrade, the win rate and the pass rate of the last two shifts; and per card, the pass rate of shifts whose hand held it against those whose hand didn't (each shift records its hand).
  - **The quota curve** (in `data/balance/balance.tres`): 41, 42, 65, 77, 87, 123, 124, 149, fitted on 480 `--quotas=0` runs per strategy on the fresh profile. Targets: the sensible player with greedy drafting (`greedy@sensible`) passes shift 1 in at least 97% of runs and shift 2 in at least 95% of the runs that reach it; from shift 3 every shift fails the same share of the runs reaching it, set so it wins 35–40% of runs; each quota is the highest whole number the required share still meets, but the curve rises by at least 1 a shift. Result: shift 1 passes 97.1%, shifts 3 to 6 and 8 fail about 13% each, and the run is won 37.5% of the time. (Since v0.34's second redraw per shift it is won 60.5% of the time; the user accepted that for now on 2026-10-18, see the v0.35 changelog row.) Two shifts are held at that floor and miss their share: shift 2 (42, one over shift 1, because its hands are no stronger than shift 1's) passes 94.2%, just under 95%, and shift 7 (124, inspected) fails about 18%; the fitter warns about both. A smoothed curve (40, 45, 58, 72, 88, 108, 125, 150) was rejected: it drops shift 2 to 91%. Skip (the starting deck, upgrades still picked) wins 22.9% and random drafting 4.6%, so drafting adds only about 15 points over skipping every reward: upgrades carry the run (the shift-8 median is 245 skipping, 257 drafting). Quotas can't widen that, so "skip at least 25 points below greedy" moves to the balance passes (#42) as a gate item, with these findings: Short belt causes 56% of the failed inspected shifts while it is a third of them, runs with Rule bender win 25% and with Category engine 61%, and Big basket is almost never picked. The card checks on the new curve (480 runs per strategy, played with the live data, which reproduce the fit exactly; pass rates are the sensible player's on shifts 2 to 8 with the card in hand against without it): Eggs is still a single point of failure (90% against 66%), and so is Milk (90% against 64%); Multipack still dominates (99.5% of the coupon-slot duel; 94% against 85%); Breakfast sticker is still near blank (6.7 under the average coupon, never the best); and a hand holding 2 for 1 passes only 68% (89% without). All of it goes to #42.
  - **Chained profiles.** `--chains=N` plays N profiles per strategy from a fresh one, run after run (at most `--chain-runs`), each run's coins buying capsules (a random machine with items left, its key item first, then at random), the list kept and joined by an aisle once it becomes listable, and new arrivals riding the end-cap as in the game. It reports the runs to unlock all 30 items (p10, median, p90). On the new curve and coins, 24 profiles of the sensible player took 27 runs at the median (23 at p10, 37 at p90), inside the 25–40 target, at 1.05 coins a run; their win rate falls from 37.5% on the fresh profile to 33% over the chain as the stock widens, for the list gate in #42 to watch.

## 10. Risks and what gets cut

| Risk | Response |
|---|---|
| Art takes longer than planned | Fewer unique packaging designs (reuse frames + icons) · simpler background · cut PNG export · an undrawn item never blocks content: a product shows the 48x48 art-pending box with its name printed in it, a coupon the real slip with its name (#75, section 6.1), so items can ship before their art |
| Coupons create one dominant combination | Simulator + limits (max cards per row, Repeat can't copy amplified values) |
| Upgrades feel weak or samey | Fewer upgrades (6) that are more distinct, rather than 8 average ones |
| Too many ceremonies for the presentation hours | The count-up, the dessert and the final receipt come first; the run intro and capsule-machine animation are cut before them (cut order below). The kiosk ceremony left the cut list when #77 merged the kiosk into the RECEIPT REWARDS machine, which is not cut: its animations play at one tempo, a click fast-forwards them, and reduced motion shortens them |
| Players skip reward and upgrade presentations (since #77, the machine's visits) | Measure `presentation_skipped`; shorten until second-run skips are under about 70% |
| Item count multiplies art (about 30 more products) | One sprite per item, reused as the figurine · cut the machine-opened aisles whole, with their machines, before any base product; the stock rule works with any number of aisles |
| The capsule machines read as monetisation | 1 coin = 1 capsule, no shop, nothing for sale; never called "gacha"; the store page states there are no microtransactions |
| The shopping list adds friction at run start | Hidden until the budget is passed, pre-filled, one click, "Surprise me". If over about 70% of lists are never changed, make "Surprise me" the default |
| One list dominates | Simulator list gate · `run_start` logs the aisles and stock size · win rate per list in the summary script |
| The first list feels like losing an aisle | The stock gets denser, not weaker; the first list is pre-filled (section 7.2: the new aisle if there is one) and new arrivals always show up (since #77: the run's first NEW ITEMS draw holds the newest one) |
| Schedule slips | Cut in this order (the kiosk ceremony, first until #77, is gone with the kiosk): PNG export → run intro → capsule-machine animation (a plain machine panel stays) → shopping-list note (a seeded random list stays) → 3rd inspection → machine-opened aisles, whole, with their machines (retune the coin amounts for the 7 capsules left in the base machines) → upgrade count. Coins and saved unlocks are cut only after all of these. **Never cut:** the scoring explanation, the counting presentation (including the dessert), bug-fixing time. |
| Confusing rules | Simplify effects before adding content |

Content freeze at the end of phase 3. No new features after that.
